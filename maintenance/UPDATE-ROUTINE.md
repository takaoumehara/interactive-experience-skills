# スキル更新ルーチン

このリポジトリの3スキルを、月1回、事実の面で最新に保つための手順書。

**この文書自体が、月次ジョブに渡す指示文である。**「## 実行指示」以下をそのままコピーして新しいセッションに渡せば、調査から提出まで完走する。

## `/refresh-skills` との関係 — 重複させない

このリポジトリには既に `/refresh-skills` がある。**役割が違うので、両方を使う。**

| | `/refresh-skills` | このルーチン |
|---|---|---|
| 起動 | **人間が思い立った時** | **月1回、自動** |
| やること | volatile マーカーの項目を検索し、**変化した点だけを報告**（`apply` で反映） | 検出に加えて、**答えを日付と出典つきで `current.md` に記録**し、履歴を残し、提出する |
| 残るもの | その場の報告 | `current.md` / `CHANGELOG.md` / コミット |
| 判断 | 反映するかを人間がその場で決める | **採否基準に従って自動で振り分け、最終判断は人間のレビュー**に回す |

**このルーチンは `/refresh-skills` を検出ステップとして内部で使う。**同じ検索ロジックを二重に書かない。`/refresh-skills` が意図的にやらないこと — 記録の蓄積、履歴、スケジュール、git — をこのルーチンが足す。

## なぜルーチンが要るのか — 腐り方の構造

インタラクティブ体験の知見は、一様に腐るのではない。**腐る速度が3層に分かれている。**

| 層 | 例 | 半減期 | 扱い |
|---|---|---|---|
| **原理** | 遅延50msで演者は身体の延長と感じる / 外的焦点は内的焦点より優れる / 「1つのルールに全予算を注ぐ」 | 5年以上 | **原則として書き換えない。** 覆すには査読論文か複数の反証事例が要る |
| **構造** | どのセンサー方式がどの場面に向くか / プロジェクションとLEDの分岐条件 / スケール別の考え方 | 1〜3年 | 世代交代が起きた時だけ書き換える。年に1〜2回 |
| **時価** | 型番、価格、バージョン番号、fps、ライセンス条件、法規制の施行日、企業の存続 | 3〜12ヶ月 | **毎月見る。`references/current.md` に隔離してある** |

この3層を混ぜて書くと、時価が腐った瞬間にスキル全体が信用を失う。だから **時価情報は各スキルの `references/current.md` 1ファイルに集約し、原理・構造の記述からは切り離してある。**

**`<!-- volatile: -->` マーカーとの関係。**各リファレンスの冒頭には、そのファイルのどの種類の記述が時間で腐るかを名指しした `<!-- volatile: YYYY-MM — ... -->` が付いている。**この2つは役割が違う。**

- **マーカー = 索引。**「このファイルのこの種類の記述は腐る」という宣言。**月次調査の対象を決めるのはこのマーカーである。全リファレンスのマーカーを読み、名指しされた項目を漏れなく調査範囲に入れる**
- **`current.md` = 答えの置き場。**「で、今はこうである」を日付と出典つきで書く

スキル実行時は「マーカーが付いた記述を使う → まず `current.md` を見る → 無いか古ければ検索」という順に流れる。**新しいリファレンスを追加した人がマーカーを付けたら、その項目は自動的に月次調査の対象になる。**マーカーの年月も、その項目を調査した月に更新する。

**月次ルーチンの仕事の9割は `current.md` の更新である。**構造層に手を入れるのは、後述の「構造を書き換える条件」を満たした時だけ。原理層は原則として触らない。

## 監視する領域と情報源

詳細な情報源リストは `maintenance/sources.md`。監視領域は7つ。

1. **姿勢推定・身体トラッキング** — モデル、SDK、メンテ状況
2. **センサー・入力機材** — 深度カメラ、LiDAR、mocap、生体センサーの入手性と価格
3. **リアルタイムエンジン・制作ソフト** — TouchDesigner / Unreal / Unity / Notch / Web / 3DGS
4. **出力機材** — プロジェクター、LED、XR、音響、GPU/計算機
5. **リアルタイムAI** — 映像生成、音声対話、オンデバイス推論の到達点と単価
6. **法規制** — EU AI Act、日本の個人情報保護法、米国の生体情報法、未成年、医療機器該当性
7. **スタジオ事例・作品・展示の潮流** — 参照スタジオの存続と体制、**新作・主要フェス・展示の傾向、体験形式の流行と飽和**、イマーシブ施設の相場と興行の実績値
   - **この領域だけ扱いが違う。**存続・買収・閉館・相場は事実なので通常どおり反映するが、**「何が流行っているか」はファイルに書き込まない。**報告に「今月の潮流」として書き、採用するかは人間が決める（後述）
8. **音・音楽** — Web Audio / Ableton / Max / SuperCollider 等の実装手段、権利処理の窓口と料率、IR素材の入手先
9. **道場・スタジオの経済** — 月謝と付加サービスの相場、サブスクの価格帯、決済と提供モデル

**この一覧は固定ではない。**各リファレンスの `<!-- volatile: -->` マーカーが名指ししている項目が、実際の調査範囲である。リファレンスが増えたらここも増やす。

## 前提の把握

1. リポジトリを clone し、maintenance/UPDATE-ROUTINE.md と maintenance/sources.md を読む。
2. 3スキルそれぞれの references/current.md を読み、front matter の
   snapshot_date（前回の調査時点）と、既に記録されている事実を把握する。
3. CHANGELOG.md の直近3件を読み、前回何を変え、何を「次回の監視対象」として
   積み残したかを確認する。積み残しは今回の調査項目に必ず含める。

## 調査

### 4-1. 検出 — /refresh-skills を使う

まず `/refresh-skills`（`refresh-skills.md` の手順）を実行する。**apply は付けない。報告だけ受け取る。**
これで volatile マーカーが名指しした項目のうち「変わったもの」「確認できなかったもの」
「選択肢が増えたもの」が出てくる。**同じ検索を自分で書き直さない。**

`/refresh-skills` が使えない環境（スラッシュコマンドが無い等）では、`refresh-skills.md` を読んで
その手順を自分で実行する。

### 4-2. 深掘り — 記録に足りない分を補う

`/refresh-skills` は「変わったか」しか見ない。このルーチンは「**で、今はいくらで、どのバージョンで、
どこで買えるのか**」まで記録する必要がある。そこで、変化が見つかった領域と、
sources.md の監視領域について、前回の snapshot_date 以降を追加調査する。
各領域は独立なので並列に走らせてよい。

**マーカーにあって監視領域の一覧に無い項目は、今回の調査に足す**
（リファレンスが後から追加された場合にここで拾える）。

調査時の絶対ルール:
- 訓練データの記憶で答えない。必ず検索し、一次情報（公式サイト、公式ドキュメント、
  npm/PyPI レジストリ、官報・省庁サイト、メーカー直販ページ）で裏を取る。
- 価格は「どこが、いつ時点で、どの通貨で表示していた価格か」まで記録する。
- 確認できなかったものは「確認できず」と書く。推測で埋めない。
- 各事実に確度（高=一次情報 / 中=信頼できる二次情報 / 低=推測を含む）を付ける。

## 採否の判断（ここが本体）

調べた変化のすべてを反映するのではない。次の基準で振り分ける。

【反映する】
- 製品・サービスが終売・終了・買収・分社した（例: Azure Kinect の EOL、
  Ultraleap の売却）。設計の前提が消えるため最優先。
- 価格が 30% 以上動いた、または価格帯の相対関係が逆転した
  （例: COB LED と SMD の価格差消滅、GPU の 2 倍高騰）。
- ソフトウェアのメジャーバージョン、ライセンス体系、料金体系が変わった。
- 「できなかったことができるようになった」あるいはその逆（例: リアルタイム動画生成の
  実用化、ARKit Body Tracking の破損）。
- 法規制の施行日・義務内容が確定または変更された。
- スキル内に名指しで書かれている製品・企業・API が、現況と食い違っている。

【反映しない】
- マイナーバージョンアップ、機能追加のうち設計判断を変えないもの。
- 発表されたが未出荷のもの（「2027年出荷予定」は current.md の「監視中」欄に書き、
  本文の推奨は変えない）。
- ベンチマークの数％の改善。
- 話題性はあるが、このスキルが扱うスケールの制作に届いていないもの。
- 単一のブログ記事・SNS投稿しか出典がないもの。
- **「新しい有力な選択肢が出てきた」だけのもの。**既存の記述が間違いになっていないなら、
  書き換えず current.md の「監視中」に置き、PR の説明で人間に報告する。
  **何を採用するかを決めるのは人間である**（`/refresh-skills` の「選択肢が増えた」と同じ扱い）。
- **作品・展示の潮流。**「今こういう表現が流行っている」は事実ではなく観測であり、
  しかも**このスキルが最も嫌う失敗（流行の模倣、既視感のある提案）を助長しうる。**
  ファイルには書かず、報告の「今月の潮流」に留める。

  ただし**例外が1つある。手法が飽和して既視感になった時は、事実として反映する。**
  `movement.md` と `studios.md` は「これは2010年頃から無数にある」のような既視感の指摘を
  持っており、**これが古いままだと、飽和した手法を新鮮なものとして勧めてしまう。**
  「ある手法が明らかにありふれたものになった」と複数の独立した観測から言える場合に限り、
  既視感の記述を更新してよい。**逆に「新しくて面白い」側は絶対に自動で足さない。**

判断に迷ったら反映しない。**間違った新情報は、古い正しい情報より有害である。**

## 反映

原則: 変更は references/current.md に閉じる。

current.md に書くこと:
- 各領域の「2026年X月時点で、実際に選べるもの・実際の価格・実際のバージョン」
- 前回からの差分（「以前は X が定番だったが、今は Y」の形で）
- 出典URLと確度
- 「監視中」— まだ反映しないが次回見るべきもの

構造層（hardware.md / software.md / movement.md / solo-scale.md / motion-tech.md 等）を
書き換えてよいのは、次のいずれかを満たす時だけ:
  (a) そこに名指しで書かれた製品・API が消えた、または壊れた
  (b) 選定の分岐条件そのものが逆転した（「安いのはA」→「安いのはB」）
  (c) 記述が事実として誤りになった
書き換える場合も、具体的な数値・型番は current.md 側に置き、構造層からは
「詳細と現在の相場は current.md」と参照させる。構造層に型番を増やさない。

SKILL.md 本体（判断基準、モード、アンチパターン、出力契約）は、
このルーチンでは原則として変更しない。変更が必要と判断した場合は、
変更せずに PR の説明に「構造変更の提案」として書き、人間の判断を仰ぐ。

分量の規律: このルーチンで各スキルの合計行数を増やしてよいのは、
前回比 +5% まで。それを超える場合は、古くなった記述・重複・
価値の薄い記述を同じ量だけ削ってから足す。**スキルは足し算で死ぬ。**

## 検証

1. bash install.sh --check が通ることを確認する
   （SKILL.md が名指しする references/assets が実在するか、frontmatter の name が
   ディレクトリ名と一致するか、current.md の鮮度）。
   **--check を付ける。付けないと ~/.claude へ配置し .skill を作り直してしまう。**
2. 変更した事実のうち、確度「高」でないものを1つずつ再検索し、裏を取り直す。
   裏が取れなかったものは記述から落とす。
3. evals/evals.json の期待値と、変更した記述が矛盾していないか確認する。
   矛盾していれば evals 側も直す。
4. git diff を通読し、意図しない書き換え・文体の逸脱がないか確認する。
   このスキル群の文体は「断定し、数字を出し、しかし前提を明示する」。
   曖昧な形容詞で埋めた記述を混入させない。

## 記録と提出

1. 各スキルの references/current.md の front matter の snapshot_date を今日の日付に更新。
   今回調査した項目を含むリファレンスの `<!-- volatile: YYYY-MM -->` の年月も今月に更新する
   （調査していない項目のマーカーは動かさない。動かすと「見た」という嘘になる）。
2. 各 SKILL.md の metadata.last_reviewed を今日の日付に更新。
   事実の更新のみなら version は据え置き、構造層を書き換えたなら minor を上げる。
3. CHANGELOG.md の先頭に今回分を追記する。書式:
   ## YYYY-MM-DD
   ### 変更
   - <何を、なぜ変えたか。出典URL>
   ### 見送り
   - <調べたが反映しなかったもの。理由>
   ### 次回の監視対象
   - <未確定で次回見るべきもの>
4. **.skill を作り直さない。**変更するのは _extracted/ だけである。
   .skill は zip なので、中身が1文字変われば毎月バイナリ全体が差し替わり、
   リポジトリが太る一方になる。**再パッケージは、人間がこのPRをマージした後に
   bash install.sh で行う「リリース」の仕事であって、月次ルーチンの仕事ではない。**
   もし .skill に差分が出ていたら、それは --check を付け忘れた事故なので
   git checkout -- '*.skill' で戻す。
5. ブランチ update/YYYY-MM を切り、コミットして push、Pull Request を作る。
   PR タイトル: 「月次更新 YYYY-MM: <最も重要な変更を1行で>」
   PR 本文: 変更の要約 / 各変更の出典 / 見送ったもの / 人間の判断が要る論点
   **main には直接 push しない。マージは人間が判断する。**
6. 最後に、変更が1件もなかった場合も CHANGELOG に「変更なし」を記録し、
   PR は作らずにその旨だけ報告する。何も変わらない月があるのは正常である。

## 人間側の役割

このルーチンは自動でPRまで作るが、**マージは人間が判断する。**とくに次は自動化しない。

- SKILL.md の判断基準・モード設計・アンチパターンの変更
- スキルの新設・統合・廃止
- 「原理」層の記述の変更
- 参照スタジオの追加・削除、および「今月の潮流」の採否（**作品の評価は事実確認では決まらない**）

月次PRを見るときの3つの問い。

1. **この変更は、明日誰かがこのスキルを使う時の答えを変えるか。**変えないなら不要。
2. **出典は一次情報か。**メーカーのマーケティング記事だけを根拠に数値を書き換えていないか。
3. **スキルは太っていないか。**足した分だけ削れているか。

## どこで実行するか

このルーチンは実行環境を選ばない指示文だが、**環境によって「静かに失敗した時に気づけるか」が変わる。そこだけが選定基準である。**

### 推奨: Claude Code の Routine（クラウド）

**Claude Code on the web の Routine（定期実行）に登録するのが最も確実。**

- **git 認証を渡す必要がない。**クラウド環境は GitHub App 経由でリポジトリスコープの認証を持っている。**Personal Access Token の発行も貼り付けも不要**で、そのまま push と PR 作成ができる
- **マシンの起動状態と無関係。**ローカル実行の最大の弱点がここで消える
- **静かな失敗が構造的に検知できる。**下記

設定:

| 項目 | 値 | 理由 |
|---|---|---|
| スケジュール | `0 0 1 * *` | **cron は UTC で解釈される。**毎月1日 09:00 JST がちょうど 00:00 UTC |
| セッション | **毎回新規** | 同じセッションに刺すと月ごとの文脈が積み上がり、前月の判断に引きずられる。**毎回まっさらが正しい** |
| 完了通知 | **push と email を有効にする** | 下記 |
| プロンプト | 自己完結で書く | 新規セッションは何も知らない。「`maintenance/UPDATE-ROUTINE.md` を読み、`## 実行指示` のとおりに実行。ブランチは `update/YYYY-MM`。main には push しない。変更ゼロなら PR を作らず報告のみ」まで明示する |

**完了通知が、ローカル実行のログの代わりであり上位互換である。**このルーチンは「変更が1件もなかった月も CHANGELOG に記録し、報告する」設計になっている（手順6）。つまり**変更のない月も通知が来る。**したがって、

> **通知が来なかった月 = ルーチンが死んだ月**

と一意に判別できる。ログは見に行かないと気づかないが、これは気づかないことが難しい。**この手の自動化が最もよく壊れる「静かに失敗して半年後に発覚する」を、運用の注意力ではなく構造で潰している。**

環境側の前提を2つだけ確認する。**このリポジトリが環境のソースとして繋がっていること**と、**ネットワークポリシーが `WebSearch` / `WebFetch` を許していること。**このルーチンは仕事の9割が検索なので、後者が通らない環境は失格である。

**いきなり Routine に入れない。**まず1回、対話セッションで走らせて出てくるものを見る。見るべきは3点 — 調査が浅くないか（一次情報に当たっているか、「確認できず」を正直に書いているか）、反映しすぎていないか（未出荷の製品を本文に書き込んでいたら採否基準が効いていない）、太っていないか。ずれていたら **`UPDATE-ROUTINE.md` の「採否の判断」を直す。プロンプトを直すのが正しい修正で、出力を手で直すのは対症療法。**

### GitHub Actions

**選ぶ理由は1つだけ。「fork した他人の環境でも同じ更新が回る」ことに価値がある場合。**設定がリポジトリに残るので、配布物としての作法を示せる。

`GITHUB_TOKEN` がワークフローに自動で渡るため PR 作成用のトークン発行は不要（`permissions: contents: write, pull-requests: write`）。Anthropic APIキーだけを Secrets に置く。コミッターは `github-actions[bot]` になる。**自分のためだけに回すなら、Routine より手間が増えるだけで得るものがない。**

### ローカルの cron / launchd — 勧めない

**動くが、壊れ方が悪い。**

- ノートPCが寝ていれば実行されない（launchd は復帰後に実行するが、cron はその月を丸ごと落とす）
- ログを残しても、**見に行く習慣がなければ失敗に気づかない。**これは注意で防げる問題ではなく、構造的にそうなる
- `claude` の絶対パスと `--allowedTools` の綴りが、CLI の更新で静かに合わなくなりうる

どうしてもローカルで回すなら、`which claude` で絶対パスを取り（cron は PATH が痩せている）、`--allowedTools "Bash,Read,Write,Edit,Glob,Grep,WebSearch,WebFetch"` で権限を絞り、ログを追記する。**そして「毎月1日にログを見る」を別途カレンダーに入れる。**それをやらないなら、この選択肢は選ばない方がいい。

### 共通の鉄則

**どの環境でも、push に失敗したら黙って終了しない。**変更内容と差分を必ず出力に残す。**静かに失敗するルーチンは、実行されていないルーチンより悪い**（更新されていると思い込ませるため）。

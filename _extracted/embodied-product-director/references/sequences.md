# 進行順序・検証・調査の設計

## 1. 進行パターンの詳細

各段階には**それが何を決めるための段階か**を必ず付ける。決定を生まない段階は削る。

### 技術先行の救出
ユーザーが技術から始めている時(「2台のカメラとAIで何かしたい」)。最も頻出し、最も失敗しやすい入り方。

1. 価値の可能性を洗い出す → 決めること: この技術が触れうる課題領域
2. 使う人と痛みを特定 → 決めること: 誰の何を解くか
3. 形式を比較 → 決めること: アプリか、設置か、道具か
4. その技術が本当に必要か判定 → 決めること: **2台目/AI/深度を落とせないか**
5. 専門スキルへ → 決めること: 領域固有の設計
6. 最もリスクの高い前提を試作 → 決めること: 続けるか方向転換するか

**この順序の要点は4番。**技術を出発点にした案件は、最後にその技術が不要だと分かることが頻繁にある。それは失敗ではなく、この順序が正しく機能した証拠である。

### 発見先行
課題が不明確な時。機会探索 → 使う人・払う人の調査 → コンセプト → 専門設計 → 実現性試作 → 価値検証。

調査を飛ばしたくなるが、ここを飛ばした案件は「作ってから顧客を探す」ことになる。ただし調査は**5人への聞き取り**で足りることが多い。大規模調査を勧めない。

### 専門先行
領域も課題も明確な時。専門スキルへ直行 → 技術的実現性 → 試作 → ユーザー検証。**この入り方が使えるなら、ディレクターは1〜2文で判断を述べて即座に道を空ける。**

### 既存コンセプトの評価
診断 → 最も強い前提 → 最も弱い前提 → 顧客と価値の確認 → 専門的批評 → MVP再設計 → 検証計画。

**先に「最も強い部分」を特定する。**弱点から入ると、守る価値のあるものまで壊してしまう。

### 既存試作の改善
観察されたユーザー行動 → 技術的性能 → 価値の証拠 → 失敗分析 → 専門的改善 → 次の試行。

**試作の証拠を見る前に全体構想を作り直さない。**既に人が触ったものがあるなら、その観察が最も価値の高い情報源である。

## 2. 検証の6種類 — 混同しない

一つの成功したデモを、事業の検証と見なさない。

| 種類 | 問い | 典型的な手段 |
|---|---|---|
| **課題の検証** | その痛みは存在し、重要か | 5〜10人への聞き取り、練習の観察、指導の同席 |
| **プロダクトの検証** | 提案するワークフローがそれを解くか | 手作業でのシミュレーション(自動化前に人が同じ出力を出す) |
| **技術の検証** | 信頼できる観測と応答ができるか | 実環境での精度測定、失敗率、確信度の分布 |
| **成果の検証** | ユーザーは実際に上達・改善するか | 前後比較、指導者による盲検評価、一定期間の追跡 |
| **事業の検証** | 買い手は導入し、払い、継続するか | 有料パイロット、継続率、更新の意思 |
| **運用の検証** | 実環境で展開・維持できるか | 現場での設営時間、スタッフだけでの運用、故障時の挙動 |

**特に区別すべき組み合わせ:** 技術の検証 ≠ 成果の検証。姿勢推定が正確でも、それが上達に繋がる保証はまったくない。身体×学習の領域で最も多い誤りがこれ。

## 3. 手作業を先に置く

自動化の前に、**人が手でやったらどうなるか**を必ず一度通す。

- 動画を見て、人が3つの改善点を書く
- それを学習者に渡す
- 学習者が実際に上達するか、価値を感じるかを見る

これで価値がなければ、自動化しても価値はない。逆にこれで価値があれば、自動化する部分が明確になる(そして、思っていたより少ないことが多い)。この工程は数日で終わり、数ヶ月の開発を救う。

## 4. 調査戦略

**決定目的を定めずに調査しない。**各調査に「これで何を決めるか」を付ける。

- **ユーザー調査** — 聞き取り、観察、練習日誌、練習セッションの分析、指導者への同行、保護者への聞き取り、業務フローの把握
- **市場調査** — 既存プロダクト、価格、顧客セグメント、流通、導入障壁、競合の空白
- **技術調査** — モデルの能力、カメラの限界、遅延、端末性能、照明、遮蔽、キャリブレーション、必要データ量
- **領域調査** — 技の定義、流派差、**指導者間の見解の不一致**、安全、カリキュラム、進級体系

領域調査の「指導者間の不一致」は特に重要。3人の指導者が同じ動画に対して異なる指摘をするなら、そのプロダクトは「正解」を持てない。その場合の設計は、判定ではなく**指導者が自分の基準を登録できる仕組み**になる。

## 5. 判断ゲート

段階の間に「何が証明されたら次へ進むか」を置く。ゲートが無い計画は、悪い方向に長く進む。

良いゲートの条件: 観察可能 / 短期間で判定できる / 失敗した時に何をするか決まっている。

例:
- 「5人の指導者のうち3人が、この出力を生徒に見せてもよいと言う」→ 満たさなければ、出力形式を作り直す
- 「1台のカメラで支持足の接地が7割以上判定できる」→ 満たさなければ、カメラ位置を変える。それでも駄目なら2台を検討する
- 「手作業フィードバックで、2週間後に指導者が改善を認める」→ 満たさなければ、フィードバックの内容設計に戻る(自動化に進まない)

## 6. 複数領域が絡む案件

正当に複数領域にまたがる案件はある(表現的なフィードバックを持つダンス学習アプリ、本番でも使える武術指導ツール、ゲーム的動機づけを持つリハビリ、没入型の業務訓練)。

扱い方:

1. **主価値を1つ特定する**
2. 副価値を特定する
3. **主担当の専門を1つ選ぶ**
4. 他の専門は、定義された特定の問いにだけ使う
5. 副次的な機能が中核プロダクトを弱めないよう監視する

```
主価値: 振付を正確に習得する
主担当: movement-learning-system-designer

副価値: 練習を情緒的に魅力あるものにする
補助: interactive-experience-collective(フィードバックの視覚言語についてのみ)
```

**すべての領域を対等に扱わない。**対等な共同担当にするのは、プロジェクトが本当にそれを要求する場合だけ。多くの場合、対等化は「決められなかった」ことの言い換えである。

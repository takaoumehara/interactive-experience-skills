## 1. カメラの台数より先に、配置を決める

**「1台か2台か」より「どこに置くか」の方が、多くの場合に影響が大きい。**同じ1台でも角度が違えば評価できる項目が変わる。

| 配置 | よく見える | 見えない |
|---|---|---|
| **正面** | 左右の対称性、開き、横方向のブレ、顔の向き | 前後の踏み込み量、体幹の前後傾、奥行き方向の伸展 |
| **側面** | 前後の重心、体幹の傾き、踏み込み、伸展の到達、膝と股関節の角度 | 左右差、回旋、片側が完全に遮蔽される |
| **斜め45度** | 両方をある程度。実用的な妥協点 | どちらも精度は落ちる |
| **俯瞰** | 足位置、移動経路、対人の距離と角度 | 姿勢のほぼ全部 |

**評価項目を決めてから配置を決める。**「とりあえず正面」で始めた案件は、後から「踏み込みが測れない」と判明して作り直しになる。技能モデル(`skill-modeling.md`)の各項目に「どの視点から観測可能か」を書き込んでおく。

## 2. 2台目を足す判断

2台目が正当化されるのは次の場合のみ。

- **中核の評価項目が単一視点で構造的に観測できない**(前後と左右の両方が不変条件に含まれる)
- **自己遮蔽が頻繁に起きる**(床技、組技、回転、体の前で腕が交差する動作)
- **奥行き方向の絶対量が評価に必要**(踏み込みの距離、間合い)
- 単眼推定の奥行き誤差が、許容帯より大きいことを**実測で確認した**

2台目が引き起こすコスト: キャリブレーション工数、同期、設営時間の増加(**導入摩擦は事業上の最大の敵**)、故障点の増加、そして「使う人が正しく設置できない」問題。

**判断の順序:** ①配置を変えて解決しないか ②評価項目を減らして解決しないか ③2台にするか。多くの案件は①か②で足りる。

**現実的な妥協案:** 1台で運用し、精度が必要な評価の時だけ「横からもう一度撮ってください」と2回撮影に誘導する。設営コストをゼロにしたまま2視点を得られる。練習後レビュー方式ならこれで十分成立する。

## 3. 単眼で構造的に取れないもの

技術力の問題ではなく原理の問題。企画段階で受け入れる。

- **力**(打撃の威力、踏み込みの強さ)— 加速度から間接推定するしかなく、精度は低い
- **接地の圧力配分**(母趾球に乗っているか)— 見えない。圧力センサーが要る
- **筋の緊張・脱力** — 見えない。武術・ダンスの熟練者が最も重視する要素がここに入るという事実は重い
- **呼吸の質** — 音では取れる。姿勢からは難しい
- **痛み、内的感覚** — 見えない。安全境界に直結
- **奥行き方向の絶対距離** — 単眼では推定。基準物体があれば改善する
- **接触したかどうか**(当たったか、組めているか)— 映像から判定するのは想像以上に難しい
- **手指**(グローブ、道着の袖、握りの中)— 覆われていれば取れない

**設計上の帰結:** 見えないものについて見えているようなフィードバックを返さない。むしろ「システムが見るのはここまで。ここから先は先生に見てもらってください」と明示的に線を引く方が、指導者からの信頼を得る。

### 種目によって難易度が桁で違う — 企画の最初に判定する

カメラAIがゴルフ・テニス・バスケットで先に成熟し、格闘技・組技で遅れているのは、開発力の差ではなく**種目の構造の差**である。

| 条件 | 難易度への効き方 |
|---|---|
| 単独で行う / 相手がいない | 易しい。**ここから始める** |
| 動作が中速で、予備動作がはっきりしている | 易しい |
| 身体が正面を向き、四肢が胴に重ならない | 易しい |
| 動作が非常に速い(突き、蹴り、スイング) | ブラーで推定が破綻(§6) |
| 四肢が胴に重なる、身体が回る | 自己遮蔽で関節が消える |
| 二人が接近・接触する | 人物の取り違え、骨格の混線 |
| 床上で身体が複雑に重なる(寝技) | **単眼では実質不可能** |
| 「当たったか」「効いたか」が評価対象 | 映像だけでは測れない |

**判定の使い方:** 下4行に該当する種目を最初の題材に選ばない。同じ武道でも、**型・単独動作・シャドー**なら上3行に収まる。**種目ではなく、種目の中の「どの練習」を対象にするかで難易度は動かせる。**これが最も効く設計判断になる。

複数カメラ、3D三角測量、軌道の物理補正まで動員してようやく扱えるのが接触競技の領域である。そこから始めない。

### カメラとIMU・圧力センサーは競合ではなく補完

| | 得意 | ほぼ見えない |
|---|---|---|
| **手首・足首のIMU** | 打撃が起きた瞬間、加速度、速度、回数、リズム。サンプリングが桁違いに速い | ガードが下がった、肘が開いた、頭が中心線に残っている、腰が回っていない、打った後に構えへ戻っていない |
| **カメラ** | **全身のフォームと姿勢。**関係と配置 | 威力、接触、圧力配分 |
| **バッグ・床のセンサー** | 衝撃、圧力配分 | 姿勢 |

**設計上の帰結:** 既存のトラッカー製品が普及している領域に「カメラで同じことをする」と言って入らない。**カメラが埋めるのは、センサーに見えていない全身フォームの側である。**両方ある案件では、IMUをイベント検出(いつ打ったか)に、カメラを質の評価(どう打ったか)に割り当てるのが素直な分担になる。

## 4. 時間軸を合わせる

学習者と参照は速度が違う。そのまま重ねても比較にならない。

- **フェーズ境界での分割が第一手。**準備・主動作・極点・回復の境界を検出し、フェーズごとに正規化して比較する。全体をまとめて時間伸縮させるより、はるかに解釈しやすい結果になる
- **境界の検出**は、速度のゼロ交差、加速度のピーク、特定関節の方向転換で取れることが多い。技によって指標が違うので、技能モデルに「このフェーズの境界は何で検出するか」を持たせる
- **DTW(動的時間伸縮)** は全体の対応付けに有効だが、結果が解釈しにくく、誤った対応を作ることがある。フェーズ分割の補助として使い、単独の主軸にしない
- **速度そのものが評価対象**の場合(極めの鋭さ、リズム)は、時間正規化してはいけない。何を正規化し何を残すかの判断が要る

## 5. 確信度制御 — 黙る仕組み

コア原則「確信が持てない時は黙る」の実装。

各フィードバックの発火条件に、次を必ずAND条件で入れる。

- 関連ランドマークの推定信頼度が閾値以上(全フレームではなく、判定に使う区間で)
- 対象部位が画角内にある
- 動作速度がモーションブラー限界以下(高速動作は`interactive-experience-collective`側の`movement.md`と同じ物理制約を受ける)
- 照明が最低条件を満たす
- フェーズ境界が検出できている

満たさない時の出力は「判定不能」であって「問題なし」ではない。**この2つを区別しない設計は、静かに間違った安心を与える。**

**撮影時のガイド**も設計に含める: 立ち位置のガイド枠、明るさの警告、画角外の警告。撮り直しを促す方が、悪いデータで判定するより常に良い。

## 6. 高速動作の物理的制約

突き、蹴り、回転、跳躍は**30fps・ローリングシャッターでは推定が破綻する。**モーションブラーで関節が消える。

対策: 60〜120fpsでの撮影(近年のスマートフォンは対応)、シャッタースピードを上げる(=明るさが必要)、グローバルシャッター、あるいはその項目を評価対象から外す。

**武術案件では、撮影fpsと照明の要件を企画の最初に確定させる。**後から判明すると、道場の照明環境という変更不能な制約に突き当たる。

## 7. 遅延予算 — どこまで即時が要るか

**この領域では、低遅延が要る場面の方が少ない。**遅延要件を先に決めておかないと、不要なリアルタイム化に実装予算を吸われる。

| 用途 | 許容遅延 | 根拠 |
|---|---|---|
| **同時性の知覚**(自分の動きに反応が付いてくる感覚) | 〜100ms | これを超えると「自分の動き」ではなく「反応」として知覚される |
| **安全に関わる逸脱の警告**(着地、頸部、体幹の捻り) | 〜200ms | 動作の途中で止められる猶予。ただし高速動作では間に合わないので、そもそも警告に頼らない設計にする |
| **リズム同期**(拍に合わせる練習) | 〜50ms | 音との同期は視覚より要求が厳しい |
| **1レップ終了ごとの結果表示** | 〜1秒 | 動作が終わってから出るので、体感上は即時 |
| **セット終了後・練習後のレビュー** | 数秒〜数分でよい | **多くの学習用途はここに収まる。**ここに収まるなら、オンデバイス即時処理は不要 |

**判定の順序:** 上の表で自分の用途がどこに入るかを先に決める → 数秒でよいなら、リアルタイム推論・低遅延通信・軽量モデルへの妥協を全部やめられる → 浮いた予算を評価の質と出力の言葉づかいに回す。

**注意:** 「常時リアルタイム採点」は遅延の問題ではなく学習効果の問題である(`learning-design.md` の依存性の問題)。遅延要件を満たせることは、常時出してよい理由にならない。

## 8. 実装形態とプライバシー

| 方式 | 利点 | 注意 |
|---|---|---|
| **オンデバイス** | 低遅延、通信不要、**動画が端末外に出ない** | 端末性能への依存 |
| **端末で特徴量抽出→クラウドで分析** | 動画を送らずに済む。分析を後から改良できる | 特徴量も個人データでありうる |
| **動画をクラウドへ** | 実装が楽、後から再分析できる | **未成年案件では実質的に採用困難** |

**道場・スクール案件では、オンデバイス処理または「動画を送らない」設計が、技術的優位ではなく営業上の必須条件になる。**保護者説明会で「動画は端末から出ません」と言えるかどうかが導入を決める。

保持方針も設計に含める: 保存期間、削除方法、誰が見られるか、退会時の扱い。指導者が生徒の動画を見られる設計にする場合、それを生徒と保護者が理解しているか。

## 9. モデル選択の考え方

### 姿勢推定は製品の1〜2層目でしかない

**「姿勢推定ライブラリを使えば製品になる」は、この領域で最も高くつく誤解である。**カメラで動作を評価する製品は、おおむね次の層で構成される。

```
1  人物検出              人を見つける
2  姿勢推定              関節を見つける          ← 既製ライブラリが担うのはここまで
3  物体検出              ボール、ラケット、グローブ、標的を見つける
4  時間方向の追跡        前後フレームで同じ人・物を追い続ける
5  動作認識              技の種類を分類する
6  フェーズ分割          構え・予備・加速・接触・戻りを分ける
7  2D→3D 復元           1台または複数台から3D化する
8  バイオメカニクス      関節角度、速度、身体連鎖を計算する
9  種目固有のルール      その競技で何が良い動きかを判断する
10 フィードバック        映像・音・文章・ドリルへ変換する
```

**工数の実体は3〜10にある。**見積と技術検証の焦点をここに置く。特に4(追跡)と6(フェーズ分割)は、動くデモと使える製品を分ける境目になりやすい。

**逆に言えば、1〜2だけで作れるものも実在する。**角度、左右差、タイミング、リズム、戻りの速さは、既製の姿勢推定だけでかなり早く形になる。**そこで止まる設計を選ぶのは、正しい判断でありうる。**

### 推定された3Dと、測定された3Dは違う

単眼から得られる3D座標は、ニューラルネットワークが**推定した**3Dであり、複数カメラで三角測量した**測定値**ではない。

- **使ってよい:** 左右差、関節角度の傾向、動作のタイミング、身体の相対的な位置関係、**同一人物の前回との比較**
- **慎重に扱う:** 拳が何cm移動したか、速度が何km/h か、衝撃が何ニュートンか、骨盤が正確に何度回転したか

**この区別を曖昧にした数値を出すと、最初は通っても、指導者に一度指摘された時点で信頼が消える。**絶対値ではなく変化と傾向で語る設計にしておくと、この問題自体が起きない。絶対値が本当に要るなら、2台以上のカメラか、専用センサーが要件になる。

### 選択肢

- **既製の姿勢推定で始める。**独自モデルの学習は、既製で何が足りないかを実測してから。実装の起点: オンデバイスなら MediaPipe(Web/モバイル/デスクトップ)、Apple Vision / ARKit(iOS)。軽量・高速に振るなら MoveNet 系(点数が少なく速い)。精度優先のオフライン分析なら HRNet / RTMPose 系。複数モデルを比較検討する基盤としては MMPose。物体検出と一体で扱いたいなら YOLO 系の姿勢モデル。手指が要るなら MediaPipe Hands / Vision の手指ランドマーク。**いずれも選定時に最新状況をWeb検索で確認する**
- **点数の多いモデルが常に良いわけではない。**全身が画面に入る距離では、指や瞳の点は小さく写り、点はあっても品質は落ちる。**必要な部位を、必要な距離で撮る方が、点数を増やすより効く**
- **必要なのは分類ではなく計測であることが多い。**「この技が正しいか」をモデルに判定させるより、角度とタイミングを計測してルールで判定する方が、説明可能で、指導者が調整でき、学習データも要らない。**ルールで足りる場面で学習モデルを作らない**
- 学習モデルが必要になる典型は、フェーズ境界の検出、技の種類の識別、ノイズの多い環境での人物検出
- 精度指標を「関節位置の誤差」で測らない。**評価項目ごとの判定一致率**(指導者の判定とシステムの判定がどれだけ一致するか)で測る。これが唯一意味のある精度である

## 10. 検証の実測項目

技術検証で必ず測るもの。

- 実環境(実際の道場・スタジオの照明と背景)での**判定不能率**
- 指導者の判定との**一致率**(項目別)
- **偽陽性率**(問題ないのに指摘した割合)— 信頼を壊すのはこちら。偽陰性より重く扱う
- 設営から撮影開始までの**実測時間**
- 使う人が自力で正しく設置できた割合

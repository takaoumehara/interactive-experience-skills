# プロダクト・事業設計

## 1. 使う人と払う人

この領域では両者が分かれるのが常態である。誰の予算から出るかまで特定して初めて設計になる。

| 構成 | 使う人 | 払う人 | 成立条件 | 主な失敗 |
|---|---|---|---|---|
| 個人向けアプリ | 学習者 | 学習者 | 継続動機が自己完結。習慣化が生命線 | 1週間で飽きる。上達実感が出る前に離脱 |
| 保護者課金 | 子ども | 保護者 | **保護者に上達が見えること**が価値 | 子ども向けに作り込み、保護者への報告を軽視 |
| 道場・スタジオ導入 | 生徒と指導者 | 経営者 | 継続率・新規獲得・単価のどれかに効く | 指導者が反対して導入が止まる |
| 指導者向け道具 | 指導者 | 指導者/道場 | 指導者の時間を実際に節約する | 生徒向け機能に開発を費やす |
| 学校・法人 | 生徒/従業員 | 組織 | 予算年度、稟議、同意、プライバシー | 意思決定に半年かかることを見積もっていない |

**指導者は門番である。**どの構成でも、指導者が反対すれば導入は止まる。指導者を「置き換える」と受け取られる説明は、たとえ事実でなくても致命的になる。

## 2. 道場・スタジオの経済

経営者が見ているのは、生徒の上達そのものではなく**継続率と新規獲得**である。提案はここに接続する。

- **継続率** — 生徒が辞める最大の理由は「上達している実感がない」と「見てもらえていない感覚」。この2つに直接効くことを示せれば強い
- **保護者への説明** — 子ども向け道場では、保護者が継続を決める。進捗レポートは経営ツールでもある
- **指導者の時間** — 個別指導の時間が足りないことが、多くの道場の構造的問題。時間を作る道具は導入されやすい
- **差別化** — 近隣の道場との差。「うちはこれがある」と言えること自体に価値がある
- **単価** — 付加サービスとして月額に上乗せできるか

**提案時の翻訳:** 「フォームを自動評価します」ではなく「先生が全員を見きれない部分を埋め、生徒に上達が見え、保護者に報告できる」。前者は技術説明、後者は経営課題への回答。

## 3. 導入摩擦 — 最も過小評価されるリスク

**クラス中に2分以上かかる準備は、実際には使われない。**技術が正しくても、摩擦で死ぬ。

摩擦の棚卸し: 機材の設置と撤収 / キャリブレーション / アカウント作成 / 生徒への説明 / 撮影の立ち位置調整 / 結果の確認と共有 / 保護者同意の取得 / 不具合時の対処。

削り方: 設置固定(毎回動かさない)/ キャリブレーション自動化 / アカウント無しで始められる / 撮影ガイドを画面に出す / 結果はその場で見ずに後で見る設計にする。

**「先生が一人で、生徒に説明しながら、2分以内にできるか」**を設計の判定基準にする。この基準を通らない機能は、どれだけ価値が高くても採用されない。

## 4. 形式の選択

| 形式 | 勝つ条件 | 注意 |
|---|---|---|
| **iOSアプリ** | 端末カメラを使う、オンデバイス処理、持ち運び、家庭での練習 | 審査。Androidを切る判断。道場のiPad共用も選択肢 |
| **Webアプリ** | 配布と試用の摩擦が最小。指導者に「このURLで試して」と言える | カメラ権限、端末差、オフライン不可 |
| **指導者ダッシュボード** | 複数生徒の管理、クラス運営、進捗の俯瞰 | 生徒側アプリと同時開発すると個人開発では破綻する |
| **道場据置システム** | 毎回同じ位置、キャリブレーション不要、設営摩擦ゼロ | 初期投資と設置交渉。1道場ずつしか広がらない |
| **既存動画への後付け分析** | 撮影行動を変えなくてよい。摩擦が最小 | 撮影条件が制御できず判定不能率が上がる |

**個人開発での定石:** 生徒向けアプリと指導者向けダッシュボードを同時に作らない。**どちらか一方に絞る。**先に指導者側を作った方が、導入の門番を味方にでき、参照フォームのオーサリング(`skill-modeling.md`)も同時に解決できることが多い。

## 5. 価格と提供モデル

- **個人向けサブスク** — 継続率が全て。上達実感が出る前に解約される構造的リスク。年額プランで初期離脱を緩和する手はあるが、価値が出ていないのに縛るのは長期的に不利
- **道場向け月額(施設単位)** — 生徒数課金より施設単位の方が導入判断が速い。予算が読めるため
- **指導者向けツール** — 時間削減が価値なので、削減時間から逆算した価格を提示できる
- **買い切り+更新** — 設置型に向く
- **道場の月謝に上乗せ** — 経営者にとって最も分かりやすい。道場が生徒から回収する構造なら、道場の売上が増える提案になる

**検証すべきは「いくらなら払うか」ではなく「誰の予算から、いつ、どういう判断で出るか」。**個人道場なら経営者の即断、フランチャイズなら本部承認、学校なら年度予算。判断プロセスが分かって初めて価格設計ができる。

## 6. MVPの切り方

**縦に切る。横に切らない。**

- 悪い切り方: 10種の技を、浅い精度で、全部評価する
- 良い切り方: **1つの技を、1つの評価項目で、完璧に扱う。**1つの道場で、1人の指導者と、10人の生徒で回す

理由: 学習効果も指導者の信頼も、深さからしか生まれない。浅く広いものは、指導者が3分触って「使えない」と判断する。

**MVPに含めなくてよいもの:** アカウント、決済、複数道場対応、カリキュラム、動画ライブラリ、独自モデル、リアルタイム処理、Android対応、多言語。

**MVPに必ず含めるもの:** 指導者が結果を見て「これは生徒に見せていい」と言える出力品質。判定不能時の正しい挙動。

## 7. 検証の順序

1. **手作業版** — 人が動画を見て3つの改善点を書き、渡す。上達するか、価値を感じるか。数日で終わる
2. **課題の検証** — 指導者5人に「毎回同じことを言わされているのは何か」を聞く。ここで全員が同じことを言えば、対象技が決まる
3. **出力の検証** — 自動生成した出力を指導者に見せ、「これを生徒に見せてよいか」を聞く。3/5が是なら次へ
4. **技術の検証** — 実環境での判定不能率と、指導者判定との一致率。特に**偽陽性率**
5. **成果の検証** — 2〜4週間後、フィードバック無しでの実行品質、または指導者の盲検評価
6. **事業の検証** — 有料パイロット。無料で使うことと払うことは別
7. **運用の検証** — 指導者だけで、こちらが立ち会わずに1ヶ月回るか

**3を飛ばして4に行かない。**技術的に正確でも指導者が見せたくない出力なら、精度を上げても事業にならない。

## 8. 拡張の順序

検証を通った後にのみ。

技を増やす → 指導者オーサリング → 進捗ダッシュボード → 複数道場 → カリキュラム連携 → 決済 → 独自モデル → 法人管理。

**プラットフォーム化は最後。**1つのワークフローが1つの道場で回り、継続的に使われ、対価が支払われるまで、プラットフォームの設計に時間を使わない。

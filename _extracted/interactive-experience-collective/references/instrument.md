# 身体を楽器にする — カメラ入力で「どんな動きでも心地よい」を作る

`sound.md` が音の設計全般（誰がタイムラインを持つか、遅延予算、権利、アクセシビリティ）を扱うのに対し、**このファイルは「身体の動きを、その場で演奏に変える」ための工学だけを扱う。**カメラやセンサーで取った身体の量が、直接その瞬間の発音になる案件で読む。

音が伴奏・環境音・演出として鳴るだけの案件では、ここは読まなくてよい。`sound.md` で足りる。

## 0. この設計が本当に引き受けている問題

「どんな動きでも気持ちいい音にする」の実体は、**演奏の失敗を減らすことではなく、出力空間から失敗を消すこと**である。外れた音が「出にくい」のではなく、**外れた音が存在しない空間を作る。**以下の第1〜5節はすべてその手段である。

**代償を先に書く。**

> 全員が同じように上手く聞こえる体験には、上達の余地が無い。

これは `pleasure.md` §9（楽しさは反復から生まれ、反復は上達の余地から生まれる）と正面から衝突する。**「ペンタトニックに拘束します」と書いて終わるのが、この領域で最も多い失敗である。**必ずどちらかを選んで書く。

- **入口だけ強く拘束する** — 最初の30秒は外れようがない。触り続けるほど拘束を緩め、音域・和声・音色の選択肢が開く
- **拘束する軸を限定する** — 音程だけは絶対に外れない。その代わり**律動・強弱・音色・空間には解像度を残す。**上手い人の出力が明らかに違って聞こえるのは、この3つのどれかである

**判断:** 通行人が数十秒触る設置なら前者、繰り返し使われるアプリや演者の道具なら後者。両方に振らない。

## 1. 拘束の4層 — どこで失敗を消すか

```
身体 → [1 平滑化] → [2 発音判定] → [3 音高の拘束] → [4 時間の拘束] → 音
```

| 層 | 消す失敗 | 手段 | 代償 / 壊れ方 |
|---|---|---|---|
| **1 平滑化** | 推定ジッタがプチノイズ・機銃射撃になる | 速度適応フィルタ、ポルタメント | 群遅延が増える。**微分すると誤差が増幅する**（§2） |
| **2 発音判定** | 位置で鳴らすと静止中に暴発する | 速度ゲート + ヒステリシス + デバウンス | 弱い動き・遅い動きが鳴らなくなる |
| **3 音高の拘束** | 不協和 | スケール吸着（Tonal.js）、和音単位での発音 | 全員が同じに聞こえる（第0節） |
| **4 時間の拘束** | もたつき、複数人でずれる | 拍への量子化 | 表現が死ぬ。**層で分ける**（`sound.md` §6） |

**効果が大きいのは3と4だが、手を抜かれるのは1と2である。**1と2が雑なまま3と4を足すと、「正しい音程で、意図しない瞬間に鳴る」という最も気持ち悪い状態になる。

### 平滑化は固定係数の EMA から始めない

固定 α の指数移動平均は、**「速い動きでは遅れ、遅い動きでは震える」を必ず両方起こす。**α を上げれば静止時のジッタが乗り、下げれば打点が遅れる。どちらに振っても片方が壊れる。

速度に応じてカットオフを動かすフィルタ（one-euro filter が代表）にすると、**静止時のジッタを潰しながら、速い動きの遅れを増やさない。**カメラ由来のランドマークを扱う場合、これが実質の既定値である。α を手で調整し続けている実装は、たいていこの選択をしていない。

音程に使う値には、加えて**ポルタメント**（目標値へ時定数で追従）を噛ませる。ジッタが「揺れ」ではなく「意図的なグライド」として聞こえる。これは誤魔化しではなく、`pleasure.md` §5 の 1/f のゆらぎと同じ効き方をする。

## 2. 打点をどう取るか — 位置ではなく、運動の反転で取る

**空中には面が無い。**「境界を越えた」で発音させると、境界付近の微振動で連打になる。ヒステリシス（越える閾値と戻る閾値を分ける）は必須だが、それだけでは強弱が出ない。

**打撃の実体は接触ではなく減速である。**

```
振り下ろし（速度が閾値を超える）→ 急減速（加速度が反転）→ ジャークの極大 = 打点
```

`movement.md` §4 の「極めは加速度のピークではなく直後の急停止で検出できる」と同じ構造。武術の極めと、空中で木琴を叩く動作は、信号としては同じものである。

### ただし、この判定は遅い

打点は**衝突が始まった後にしか確定しない。**カメラの 30〜60ms に、判定のための1〜2フレームが上乗せされる。楽器としては致命的になりうる。

**対策は、下降のピーク速度を検出した時点で先に鳴らすこと**（`sound.md` §4 の予測発音の具体形）。速度が十分大きい時だけ適用し、確定は後から来る。誤発音は「速度が大きい時だけ」という条件で抑える。**それでも足りないなら、その企画は連続励起型に倒すべきである**（`sound.md` §3）。

### 何を、何に割り当てるか

- **ピーク速度 → ベロシティ（音量）**
- **ジャーク → 音色の明るさ（フィルタのカットオフ、倍音量）**

この2つを別のパラメータに割り当てると、同じ「叩く」でも表情が出る。片方だけに繋ぐと、強い/弱いの1軸しか無い楽器になる。

### 実装上の落とし穴（全部踏む）

- **正規化座標の速度は、カメラからの距離に依存する。**近くにいる手は、同じ実速度でも数倍速く見える。しきい値を固定すると、立ち位置が変わっただけで鳴らなくなる。→ MediaPipe Tasks の **world landmarks（メートル単位、原点は手の幾何中心）**を使うか、肩幅・手のひら幅で正規化する
- **dt はフレームごとに揺れる。**タイムスタンプで割る。フレーム番号や固定の 1/30 で割ると、フレーム落ちのたびに速度が跳ねて誤発音する
- **微分を重ねるとノイズが増幅する。**位置→速度→加速度→ジャークは3回微分であり、推定のわずかな揺れが支配的になる。**ジャークをしきい値の判定に使うなら各段で平滑化する。**安全側の設計は、ジャークは「鋭さ」の連続量にとどめ、発音の判定そのものは速度と加速度で行うこと
- **デバウンスは必須だが、上限を音楽的な最小音価に合わせる。**100〜150ms 固定にすると、速い連打が物理的に不可能な楽器になる
- 検出が落ちた（手が枠外に出た、遮蔽された）フレームは、速度0ではなく**未定義**として扱う。0にすると復帰時に巨大な加速度が出て暴発する

## 3. 精度が足りない時は、出力の粒度を上げる

**この分野で最も費用対効果が高い一手。**

空中で単音を正確に撃つのは難しい。だが、**撃つ単位を大きくすれば、同じ精度で成功率が上がる。**

| 単位 | 人が決めること | 系が決めること |
|---|---|---|
| 音 | どの音か（難しい） | — |
| **和音** | 手の高さ・形でコードを1つ | 構成音、ボイシング |
| **フレーズ** | 動作の方向と速さ | アルペジオの音列と流れる速さ |
| **音域** | 「このあたり」 | どの音が鳴るか |

**入力の解像度が足りない時、出力の解像度を下げるのではなく、単位を大きくする。**粒度を上げても、強弱・タイミング・空間の広がりに解像度を残せば、第0節の「上達の余地」は消えない。

**カスケード（ずらし）を必ず入れる。**複数音を同時に撃つと機械的に聞こえる。10〜30ms ずつずらすだけで、指を滑らせて撫でたように聞こえる。コストゼロで最も効く一手であり、`pleasure.md` §4 の Juice リストと同じ位置づけ。

## 4. 部位ごとに役割を割り当てる — 成立条件は一つだけ

姿勢＝低域と拍、手＝和声、指＝旋律、顔＝空間、という階層分担は魅力的に見える。だがこれは、SKILL.md のアンチパターン「取得できる点を全部反応させること」と紙一重である。

> **成立条件は、部位ごとに時間スケールが違うこと。**

| 部位 | 時間スケール | 役割の例 |
|---|---|---|
| 姿勢・重心 | 数秒〜数十秒 | 調、低域、密度、場面 |
| 腕・手の広がり | 拍〜小節 | 和声、空間の広さ、フィルタ |
| 指先 | 瞬間 | 発音、装飾 |
| 顔・呼吸 | 数秒〜連続 | 残響、音色の質感 |

**同じ時間スケールで4部位に割り当てると、何を動かしても全部が動く=何も効いていない、に転ぶ。**時間スケールを分けられないなら、主入力を2〜3に絞る方が常に強い。

**帯域も同時に配る**（`sound.md` §5）。低域を担う系統は1つだけにする。2系統が同じ音域に来た時点で、両方が濁る。

## 5. 連続入力にスケールを効かせる — 吸着ではなく引力

テルミン型（手の位置がそのまま音程）に完全な量子化をかけると、**連続励起型の唯一の価値である連続性が死ぬ。**階段状に音程が飛ぶ楽器になり、遅延に強いという利点だけが残って表現が消える。

正しい形は、**吸着ではなく可変の引力**である。

- 音階の近傍で引力を強める。引力の強さを 0〜1 の連続量として持つ
- **速く動いている間は引力を弱め、止まりかけたら強める。**意図的なグライドは残り、止めた場所は必ず音階に乗る
- **引力は音程だけに効かせる。**音量・音色・定位は連続のまま
- 和声が動く構成（`sound.md` §6）なら、引力の目標も一緒に動く。**同じ動きなのに景色が変わる**のはここで起きる

## 6. メインスレッドから音へ — 2つの経路を混ぜない

MediaPipe はメインスレッド（30〜60fps、フレーム落ちする）、音は AudioWorklet（サンプル単位、止まってはいけない）。**離散イベントと連続パラメータを同じ経路で送らない。**

| 送るもの | 経路 | 理由 |
|---|---|---|
| 発音、停止、和音の切替 | `port.postMessage()` | 頻度が低く、順序が保証される |
| 位置・角度・距離などの連続量 | **AudioWorkletNode の `AudioParam`**（`parameterDescriptors` + `linearRampToValueAtTime`） | a-rate なら `process()` に 128 サンプル分の配列が届き、補間がブラウザ側で行われる。ジッパーノイズが原理的に出ない。**cross-origin isolation が要らない** |
| どうしても自前で大量に共有する | `SharedArrayBuffer` | 下記の代償を引き受ける場合のみ |

**既定は AudioParam である。**SharedArrayBuffer を最初から選ぶ設計をよく見るが、代償が重い。

- **`SharedArrayBuffer` は cross-origin isolation（`COOP: same-origin` + `COEP: require-corp`）が無いと存在しない。**この2ヘッダを入れると、**CORP/CORS を満たさない外部リソース（CDN、埋め込み動画、フォント、解析タグ）が全部落ちる。**「展示ページにタグを1本足したら音が死んだ」という壊れ方をする。設置案件では特に高くつく
- **`Atomics` は整数の TypedArray にしか使えない。**`Float32Array` に `Atomics.load` を呼ぶと TypeError になる。float を渡すなら `Int32Array` + ビット再解釈にするか、素の読み書きで妥協する（音のパラメータなら1フレームのティアリングは実害が無いことが多い。**ただし「アトミックにやっている」と誤解したまま書かないこと**）

**ワークレット側で必ずやること**

- **パラメータをサンプル単位で補間する。**ブロック境界で値を飛ばすとジッパーノイズが出る（AudioParam を使えば無償で手に入る）
- **`sampleRate` は `AudioWorkletGlobalScope` のグローバルにある。**48000 を直書きしない。端末で 44.1k と 48k が混在する
- 平滑化の時定数はサンプルレートから計算する。係数を直書きすると、端末によって手触りが変わる

## 7. 音源方式の選び方（`sound.md` §4 の表の運用）

| 方式 | 実務上の位置づけ | 代償 |
|---|---|---|
| **サンプラー** | 最短で説得力が出る。3〜5音程あれば間はピッチシフトで埋まる | 1オクターブ以上動かすと質感が壊れる。ロード時間と配布重量（`software.md`） |
| **物理モデリング** | 身体の量（速度、圧、距離）がそのままパラメータになる。**マッピングを作り込まなくても対応が身体に伝わる** | 音色の当たり外れが大きい。「本物っぽさ」では選ばない |
| **FM / 加算合成** | 金属・打楽器の非整数倍音。ファイル不要で即起動する | 音作りの試行回数が要る |

**どれを選んでも、アタックの速さが遅延の見え方を決める**（`sound.md` §4）。方式の選択より先に、アタックを何msにするかを決める。

## 8. 器の選択 — Web でどこまで行くか

- Web Audio + AudioWorklet で足りる。DSP を C++/Rust/Faust/RNBO から wasm にして worklet で回す道もある（`sound.md` §7）
- **Web MIDI は Safari と iOS で使えない**（2026-08 時点で実装が無く、公開されたロードマップも無い）。**外部音源・DAW・ハード連携を前提にした企画は、iPhone / iPad / Mac の Safari を最初から対象外にするか、器をネイティブにする。**後から気づくと、対象端末の想定ごと崩れる
- 楽器的な体験で 30ms を本当に切る必要があるなら、実装を削り込むより**器を変える判断が先**（`sound.md` §7）
- iOS はユーザー操作の直後でないと `AudioContext` が解錠されない。`latencyHint: 'interactive'` で作る（`sound.md` §7）

## 9. 検証 — 「気持ちいい」と言わせない

`pleasure.md` §11（初見3人・各30秒、要素を切って当てさせる）に加えて、楽器特有の3つ。

1. **同じ動きを10回。**10回とも同じ音が出るか。出ないなら、原因はしきい値の距離依存かフレーム落ちのどちらかである（§2）
2. **わざと下手に動かす。**乱暴に、震えながら、遅すぎる速度で、枠の端で。**この4つで不快な音が出ないことが「どんな動きでも」の実体である。**うまく動いた時に良い音が出るのは当たり前で、検証の対象ではない
3. **音だけ録って、映像なしで聴く。**音楽として聴けないなら、`sound.md` §1② の「音楽の層」が無い。効果音が並んでいるだけである

## 10. アンチパターン

- 位置だけで発音させること / ヒステリシスもデバウンスも無いまま境界判定を使うこと
- 打点をジャークだけで取り、しきい値をカメラからの距離で正規化しないこと / 平滑化していない信号を3回微分してしきい値に使うこと
- `dt` を固定値で割ること / 検出ロスのフレームを速度0として扱うこと
- **「どんな動きでも成功する」を作った結果、上達の余地を消したこと**（第0節の代償を書かずに済ませること）
- 部位ごとの役割分担を、時間スケールを分けずに行うこと（=全点に反応させているのと同じ）
- 連続励起型の入力に完全な量子化をかけて、連続性という唯一の価値を消すこと
- `SharedArrayBuffer` を既定にすること / COOP・COEP を入れた後に外部タグを足して音を殺すこと / `Float32Array` に `Atomics` を呼ぶこと
- AudioWorklet で 48000 を直書きすること / ブロック境界でパラメータを飛ばすこと
- Web MIDI を前提にして、気づかないうちに iOS と Safari を落とすこと
- 複数音を完全に同時に撃つこと（10〜30ms のずらしを省くこと）

## 11. 出力構成（身体入力が楽器として働く案件で、選んだモードに重ねる）

1. **拘束の設計** — 4層それぞれで何を消し、何を捨てたか
2. **上達の余地** — 入口だけ拘束するのか、拘束する軸を限定するのか。30秒後と30分後で何が違うか
3. **打点の取り方**、または連続励起型であることの宣言。遅延の内訳と、予測発音を使うかどうか
4. **出力の粒度**（音 / 和音 / フレーズ / 音域）と、残した解像度
5. **部位の割り当て**と、部位ごとの時間スケール・帯域
6. **スレッド構成**（AudioParam か SharedArrayBuffer か。SAB なら cross-origin isolation が何を壊すか）
7. **検証** — 下手に動かした時に何が鳴るか

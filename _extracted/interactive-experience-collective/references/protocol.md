# 実行プロトコル Step 1〜9 と分析レンズ

SKILL.md の Step 0(スケール判定・野心の天井・モード選択)を終えた後に読む。**モードB(コンセプト開発)/ C(体験ブループリント)/ E(プロトタイプ計画)/ H(フル体験ディレクション)では必読。**モードA/D/F/Gでは、扱っている問いに関係するステップだけを拾う。

## Step 1 — 体験命題を一文で定義する(モードB/C/Hでは必須)

「誰が / 何をすることで / 何を感じる・理解する・変化させるか」を含む一文。スローガンではなく設計判断に使える文にする。

例: 「参加者が互いの動きで一つの環境を育て、自分の行為が他者の世界にも影響していることを身体的に理解する体験。」

## Step 2 — 追加する前に診断する(既存案の改良時は必須)

改善依頼に対して即座にアイデアを足さない。まず判断する: 最も強い部分 / 体験価値を弱めている部分 / 不足 / 不要 / 最大の機会 / 最も危険な前提。改善案は問題との因果関係が明確でなければならない。

## Step 3 — 中心インタラクションを設計する

体験の心臓部は次の形式で定義する。これが曖昧な提案は必ず弱い。

**Trigger → Interpretation → Response → Transformation → Residue**

- **Trigger**: 人が行うこと(中心となる動詞は何か。触れる/歩く/振る/見る/話す/協力する/静止する)
- **Interpretation**: システムが何をどう解釈するか(座標だけでなく、質・強度・意図まで取れないか)
- **Response**: 何秒以内に何が返るか(即時フィードバック)
- **Transformation**: 環境・物語・作品が蓄積的にどう変化するか
- **Residue**: 体験後に何が残るか(記憶、痕跡、記録、持ち帰るもの)

「センサーを使う」ではなく「人と環境の関係がどう変化するか」として記述する。誤検出・未検出時の振る舞いも必ず定義する。身体・動きを扱う場合は、`movement.md` の身体版フレームワーク(Practice → Signal → Quality → Mapping → Feedback → Evolution)へ展開する。

## Step 4 — 署名的振る舞い(Signature Behavior)を一つ特定する

**機能を並べるのではなく、記憶に残る振る舞いを一つ決める。**これがプロジェクトの背骨になる。条件は次の通り。

- 一文で説明できる / 見た瞬間に知覚できる / 他プロジェクトと混同されない
- ユーザーの行為と直結している / 複数の場面で再利用できる / 視覚とシステム全体を支えられる強度がある

例: 突きが視覚環境全体を物理的に押しのける。踊り手のバランスが一時的な建築を生成する。呼吸がデジタル物質を凝結・発火・溶解させる。2人の間に張力の場が可視化される。部屋が人の通った場所を記憶し、一日かけて集合的な絵になる。

最初のプロトタイプは、機能リストではなくこの振る舞い一つを中心に作る。**署名的振る舞いの強度は、機能の数より常に重要。**

## Step 5 — 形式(Build Form)を比較する

技術スタックを決める前に、**このアイデアが最も強くなる器**を比較する。同じ発想が、形式を変えるだけで劇的に強く・安く・広く届くことがある。

iOSアプリ / iPadアプリ / Webアプリ / デスクトップアプリ / ブラウザゲーム / モバイルAR / カメラ+プロジェクターの1室設置 / カメラ2台のパフォーマンスシステム / 演者のための道具 / 観客向け作品 / 学習・トレーニング体験 / 映像生成ツール / ライブ用の視聴覚楽器

判断は次の問いで行う。空間のスケールそのものが体験の本質か? 一人になれることが価値か? 何度も繰り返し使われることが価値か? 演者が使う道具か、観客が見る作品か? 配布されることに意味があるか?

選定は明示する。「これは会場設置ではなくアプリであるべき」「これは演者のための道具であって観客向け作品ではない」といった判断を、理由とともにはっきり言う。

**スケールSの詳細な形式比較表は `solo-scale.md`。**

## Step 6 — 最小有効技術を選ぶ

望む体験を実現できる、最も単純で堅牢な構成を優先する。上から順に検討し、必要になった時点で止める。

1. センサーなしで成立するか → 2. 単純な入力(ボタン、圧力、近接)で成立するか → 3. 既存ライブラリ/ルールベースで成立するか → 4. カメラ1台のCVで成立するか → 5. カメラ2台/深度が必要か → 6. 機械学習・生成AIが本当に必要か → 7. 専用ハードウェアが必要か

技術を使うこと自体を価値にしない。特定ツールを最初から前提にしない。**自作ハードを提案する前に、既製の民生機器で試す。**サーバーを足す前に、ローカル処理で足りないか確認する。AIを足す前に、決定論的な反応の方が気持ちよくないか確認する。

**逆方向の注意:** 単純さを追求するあまり体験の核が死ぬなら本末転倒。カメラ1台で遮蔽により中心インタラクションが不安定になるなら、2台にする判断を躊躇しない。ステップを上がる判断も明確な理由とともに下す。

## Step 7 — 複数案を出す場合は体験原理を変える

表面的なバリエーションではなく、**ユーザーの行為 / 感情のピーク / 物語構造 / 空間構造 / 社会的関係 / 技術方式 / 形式 / 事業モデル / 制作規模**のいずれかが異なる2〜3案にする。企画・探索段階ではこの分岐を惜しまない — ここが提案価値の大部分を生む。出したら必ず推奨案を明示する。全案を同等に並べて判断をユーザーに丸投げしない。

## Step 8 — 技術ではなく体験をプロトタイプする

不確実性の高い前提を潰す順序で計画する。ただし検証項目を「技術的に動くか」に留めない。

検証すべきは: その行為が**気持ちいい**か / フィードバックが身体と繋がって感じられるか / 意図した動きの質が表現されているか / 何が変わったか理解できるか / 反復が習熟を生むか退屈を生むか / 演者やユーザーがシステムに応じて振る舞いを変えるか / 傍から見て関係が理解できるか / 記録して人に見せたくなる結果が出るか。

**技術的な検出に成功していて身体感覚が弱いプロトタイプは、失敗したプロトタイプである。**

## Step 9 — 出力前セルフチェック(内部処理)

SKILL.md の3項目の共通チェックに加えて、企画・設計を出す時は次も通す。

- 中心思想を一文で言えるか / 署名的振る舞いが特定できているか / 行為と反応の因果が理解できるか
- 初見の人が説明なしに参加方法を学べるか / 子ども・高齢者・身体特性の異なる人も参加できるか
- 予測可能性と驚きのバランスがあるか / 認識精度に体験全体が依存していないか / 故障時に安全に縮退できるか
- 実際の制作者・運用者がこれを維持できるか / 体験の中心が技術デモになっていないか
- 一度見たら終わりの体験になっていないか / 既存作品の表面的模倣になっていないか
- 成功を観察または計測できるか / 制作費と運用費に見合う効果があるか

## 分析レンズ(必要なものだけ起動。ただし企画段階では惜しまず横断する)

単純な依頼なら1〜2個、企画レベルなら4〜6個を横断してよい。専門家会議形式や人格別コメントとして出力せず、統合された一つの回答にする。

| レンズ | 中心的な問い |
|---|---|
| **Purpose & Meaning** | 技術を取り除いても成立する中心思想は何か。体験前後で認識や行動がどう変わるか |
| **Experience Architecture** | 最初の3秒で何が理解されるか。ピークはどこか。終了後に何が残るか。一人/複数/観客で体験がどう変わるか |
| **Creative Direction** | 一目で識別できるビジュアル原理。動きの性格と時間感覚。音が装飾でなく行動フィードバックとして機能しているか |
| **Interaction Design** | Step 3 の5要素。初心者と熟練者の双方に発見があるか。人数増加で豊かになるか壊れるか |
| **Independent Production** | 1人で作り、1人で保守できるか。価値の大部分を生む機能はどれか。計画上は立派だが体験にほとんど寄与しない機能はどれか。既製品で自作を代替できるか。複雑さをハードからソフトへ、実行時から事前計算へ移せるか |
| **Embodied Translation** | 関節座標を超えて、この動きの何が意味を持つのか。熟練者には見えて一般の観客には見えないものは何か。システムは演者に従うのか、抗うのか、記憶するのか |
| **Strategy & Value** | 何として機能するのか(集客装置/学習装置/ブランド体験/作品/商品/ポートフォリオ)。再訪理由。共有が体験を損なわず自然に起きるか |
| **Technical Architecture** | 入力→認識→状態管理→表現生成→出力→通信→記録→監視→フォールバック。選定基準は反応速度・同時人数・保守性・期間・予算 |
| **Physical Systems** | 視認距離、環境光、音の干渉、センサー死角、電源・熱、導線と滞留、安全、キャリブレーション、再起動手順、消耗品 |
| **Critical Evaluation** | Step 9 のチェック項目。問題の指摘だけで終わらず必ず改善方法を示す |

# 個人開発・低予算スケールで最高値を狙う

<!-- volatile: 2026-07 — Web / iOS のフレームワークと API 名、民生機材の性能、予算帯ごとの到達点、端末の処理能力。 -->

大規模設置の縮小版を作ってはいけない。**制約が有利に働く体験の型を選ぶ**のが個人開発の戦略である。

## 1. 個人スケールが構造的に勝てる領域

大規模設置には原理的にできないことがある。ここを狙う。

| 個人スケールの強み | 大規模設置の弱み | 設計への活かし方 |
|---|---|---|
| **配布性** | 物理的に来場が必要 | Webなら世界中に一瞬で届く。URLひとつが会場 |
| **1人称の密度** | 常に他人がいる。1人になれない | 深く静かな体験、内省、個人データの利用 |
| **持続時間** | 回転率のため数分で追い出す | 数日〜数年にわたる体験(毎日少しずつ変化する等) |
| **反復と改良** | 開幕したら変えられない | 毎週更新できる。ユーザーの反応で作品が育つ |
| **親密なデータ** | 匿名の通行人しか扱えない | カメラロール、位置履歴、心拍、日記、連絡先 |
| **手の届く距離** | 立入禁止線の向こう | 触れる、持つ、顔に近づける、息をかける |
| **失敗の許容** | 事故ると数千万が飛ぶ | 実験的・攻めた表現ができる |

**選定原則:** 「大きくできないから小さくする」ではなく、「小さいからこそ成立する体験は何か」から発想する。1人でしか成立しない体験は、1000人同時の体験より強いことがよくある。

## 2. 形式(Build Form)を先に比較する

技術スタックより先に、**このアイデアが最も強くなる器**を決める。同じ発想が形式を変えるだけで劇的に強くなることがある。

| 形式 | この形式が勝つ条件 | 注意 |
|---|---|---|
| **Webアプリ** | 配布と共有が価値。試してもらう回数が質を上げる。審査を待てない | 端末差・熱・権限。GPU負荷の可変設計が必須 |
| **iOS/iPadアプリ** | 端末を身体の延長として振る・かざす。触覚が要る。オフライン。ARKit/LiDARを使う | 開発者登録と審査。Androidを切る判断 |
| **デスクトップアプリ** | 重い処理、外部機器接続、演者用の道具 | 配布と導入の摩擦が大きい |
| **モバイルAR** | 現実空間との重ね合わせが本質。屋外・移動を含む | 屋外の明るさ、電池、腕の疲労(3分が限界) |
| **カメラ+プロジェクター1室** | 全身のスケール、複数人の共在、空間そのものが素材 | 暗さの確保が全て。会場が要る |
| **カメラ2台のパフォーマンスシステム** | 遮蔽・回転・床技を含む身体表現。演者との協働 | キャリブレーションと同期。設営時間 |
| **演者のための道具** | 反復使用され、稽古で育つ。専門家が価値を判断する | 観客向けの見栄えと要件が違う。混同しない |
| **学習・トレーニング体験** | 上達が計測でき、繰り返す動機がある | 事業化の道が最も見えやすい形式 |
| **映像生成ツール** | 出力される映像そのものが成果物。リアルタイム性は不要かもしれない | 「リアルタイムでやる意味があるか」を毎回問う |
| **ライブ用の視聴覚楽器** | 演奏される。習熟の余地が価値 | 遅延要件が最も厳しい |

**判断の問い:** 空間のスケールそのものが体験の本質か / 一人になれることが価値か / 何度も使われることが価値か / 演者の道具か観客の作品か / 配布されることに意味があるか / 実はリアルタイムでなくてよいのではないか。

選んだら理由とともに明示する。「これは設置ではなくアプリであるべき」「これは観客向け作品ではなく演者の道具にすべき」と言い切ることが、最も価値の高い助言になることが多い。

## 3. 民生機器を表現の楽器として見る

スマートフォン、Webカメラ、ブラウザ、マイク、ゲームコントローラを「制約」としてだけ見ない。潜在能力を洗い出す。

映像、姿勢推定、手・顔のトラッキング、光学フロー、物体追跡、深度推定、マイク入力、声と呼吸の検出、加速度、ジャイロ、端末の向き、タッチの圧力とジェスチャー、触覚、画面輝度、フラッシュライト、空間オーディオ、ローカルネットワーク、端末間同期、ブラウザ間通信、外部ディスプレイへのキャスト。

**創造的な機会は、少数のありふれた能力を、見慣れない形で一貫して組み合わせた時に生まれる。**新しいセンサーを探すより、手持ちの3つの入力の組み合わせ方を探す方が、個人開発では圧倒的に効率が良い。

## 4. Webアプリ単体でできること(予算¥0〜)

ブラウザは今や本格的なリアルタイム表現環境である。インストール不要・審査不要・即共有という配布上の優位は、技術的な制約を補って余りある。

**取れる入力**
- カメラ(`getUserMedia`) → 姿勢/手/顔/セグメンテーション(MediaPipe Tasks for Web が第一候補。**ライブラリの現行メンテ状況とfpsの天井は `current.md` を見る** — 「動くライブラリ」と「メンテされているライブラリ」は別物である)
- マイク → 音量、周波数解析、ピッチ検出、音声認識(Web Speech API)
- 端末センサー → 加速度・ジャイロ(`DeviceMotionEvent`)、方位、位置情報
- タッチの圧力・面積・複数指、ポインタの速度
- 他端末との通信(WebRTC / WebSocket)→ その場の複数人が1つの画面を共有

**出せる出力**
- WebGL / WebGPU(Three.js、regl、生シェーダー)。GPU計算も可能
- Web Audio API — 単なる再生ではなく合成・空間化・リアルタイム音響処理
- WebCodecs で動画の実時間処理・書き出し
- 端末の振動(`navigator.vibrate`)

**ブラウザだからこその表現**
- URLに状態を埋め込んで作品を送り合う
- 複数端末を並べて1つの絵を作る(端末の物理配置をUIにする)
- QRで即参加。会場設営ゼロで多人数参加が成立する
- 同じ作品が、PC・スマホ・プロジェクター投影で別の体験になる

**限界を先に知る:** ブラウザの姿勢推定には実効fpsの天井がある。中位以下のAndroidでは重いモデルが10fps台に落ちるため、**軽量モデルでの実測fpsを設計の天井に置く**(`current.md`)。iOSのモーションセンサーはユーザー許可が必要。バックグラウンドで動かない。音声再生はユーザー操作起点が必須。GPUは端末差が大きいので、負荷の可変設計(パーティクル数を実測fpsで調整)を必ず入れる。

## 5. iOSアプリ単体でできること(予算¥0〜、要開発者登録)

スマートフォンは、10年前なら数百万円した機材の集合体である。

- **ARKit** — 平面検出、ワールドトラッキング、フェイストラッキング(TrueDepthの表情ブレンドシェイプ)、People Occlusion。**ボディトラッキング(3D関節)は OSバージョンにより機能不全の報告がある。企画のクリティカルパスに置く前に実機で検証すること(`current.md`)**
- **LiDARスキャナ**(**Pro系のみ。世代を重ねてもPro限定が続いている — 「全ユーザーが持っている」と仮定しない**) — 数m範囲の深度取得。ポイントクラウド、空間メッシュ化、暗所でも動作。**ポケットに入る深度センサー**であり、これを持っていることの価値を過小評価しない
- **Vision** — 姿勢、手(指関節)、輪郭、物体追跡。オンデバイスで低遅延
- **Core ML** — 自作モデルをオンデバイス実行。ネットワーク不要、プライバシー保護、低遅延
- **Metal** — シェーダーによる高速な映像処理・生成
- **AVFoundation** — 120/240fpsのハイスピード撮影、マルチカメラ同時使用(前面+背面)

**表現上の強み**
- 端末が手の中にある = 身体の延長として振る、傾ける、かざす、覗く
- 前面カメラと背面カメラを同時使用 → 「見ている自分」と「見られている世界」を同時に扱える
- 触覚(Core Haptics)の解像度が高い。映像と音と振動の三位一体は、大型設置より濃密な体験を作れることがある
- 常に持ち歩かれる = 数ヶ月にわたって育つ作品が作れる

## 6. カメラの構成別にできること

### カメラ1台
- 姿勢・手・顔の推定(2D + 推定3D)
- シルエット抽出(セグメンテーション)→ 影絵、粒子化、置換
- フレーム差分による動きの検出(最も軽く最も堅牢)
- 光学フロー → 動きの方向と速度の場を取得。人を検出せずに「動き」だけを扱えるので、複数人・非人間・布や煙にも効く

### カメラ2台 — ここから質が変わる
1. **ステレオ深度** — 視差から実距離を得る。単眼推定と違い絶対スケールが取れる。前後の動きが正確に扱える
2. **オクルージョン解決** — 90度離して設置し、片方から見えない部分をもう片方で補う。踊りの床技や武術の組技では単眼は必ず破綻する。2視点の融合で3D姿勢の精度が劇的に上がる
3. **役割分担** — 1台をトラッキング専用(低解像度・高fps・広角)、1台を記録/出力専用(高画質・演出向きの画角)にする。**記録用カメラの画角を先に決めてから体験を設計する**のは個人開発で極めて重要(後述)
4. **時間差** — 同じ被写体を撮り、片方を遅延させて重ねる。過去の自分との共演
5. **内と外** — 1台を被写体に、1台を観客/環境に向ける。相互の関係を作品化する

**実装上の注意:** 2台の同期。USBカメラ2台なら独立クロックのためフレームがズレる。速い動きを扱うならハードウェア同期かタイムスタンプ補正が必要。ステレオは事前キャリブレーション(チェッカーボードで内部・外部パラメータ取得)が必須。ベースライン(2台の間隔)は対象距離の1/5〜1/10が目安。

### カメラ + プロジェクター
2台目のカメラより安く効く組み合わせ。投影面をカメラで見ることで、**投影された光そのものをインタラクションにできる**。キャリブレーション(投影座標とカメラ座標の対応)は自動化必須(グレイコードパターン投影で数分)。

## 7. 予算帯別の到達点

| 予算 | 構成 | 到達できるもの |
|---|---|---|
| **¥0** | Web + 手持ちの端末 | 世界中に配布可能なインタラクティブ作品。多人数同時参加もWebSocketで可能 |
| **〜5万** | 上記 + 中古プロジェクター or 大型ディスプレイ + 暗幕 | 1室のインスタレーション。**暗室 + 1台の投影は費用対効果が最も高い** |
| **〜15万** | + ヘイザー(スモーク)、簡易音響(2〜4ch)、三脚・リグ | 光が体積を持つ。プロジェクター光線が彫刻になる。**ヘイザーは投資対効果が異常に高い単一機材** |
| **〜30万** | + 深度カメラ or 2台目カメラ + GPU付きPC | 精度の高い身体トラッキング、ステレオ、リアルタイム生成 |
| **〜100万** | + 中古の明るいプロジェクター複数、簡易LED、IMUスーツ | 多面投影、公演レベルのパフォーマンス連動 |

**この表の前提について:** 予算帯の到達点は**機材価格の変動に直接影響される。**とくに計算機(GPU付きPC)は価格が大きく動くため、〜30万/〜100万の帯は現況で組み直す必要がある。現在の相場は `current.md`。**一方、¥0〜15万帯の結論(暗室+1台の投影、ヘイザー)は価格変動に強く、今も有効である。**

**優先順位の原則:** 機材を増やすより、**暗さ・静けさ・広さ**を確保する方が体験は良くなる。同じ映像でも、環境光のある部屋と完全暗室では別物になる。次点は音響。安いスピーカー2本を4本にするより、1本を良いものにして低域を出す方が効く。

## 8. 個人開発で最も効くレバー

**1. ドキュメント映像が成果物である。**
個人スケールでは、実際に体験する人より映像を見る人の方が100倍多い。だから**撮影を後付けにしない**。最初から「この画角でこう見える」を設計する。カメラ位置を固定し、その視点で最も美しい構図とタイミングを作る。d'strictのアナモルフィックが強いのは、正面1点から見た時の完璧さに全振りしているからで、これは個人開発が最も真似すべき戦略である。

**2. 1つのルールに全予算を注ぐ。**
Rain Room型 — 「雨はあなたを避ける」のように、一文で言えるルール1つだけで成立する体験。機能を増やさず、その1つの精度・応答・美しさに全リソースを集中する。個人開発で複数機能を並べると全部が中途半端になる。

**3. 素材で質感を買う。**
CGで高級感を出すのは高い。実素材は安い。霧、水、粉、布、鏡、和紙、植物、砂。プロジェクションを実素材に重ねた時の質感は、GPUでは到達できない。**予算¥3,000の霧が、¥300,000のGPUより見た目に効くことがある。**

**4. 音を後回しにしない。**
個人開発で最も多い失敗が、映像に9割・音に1割の配分。体感的な没入への寄与は音の方が大きい。特に低域(20〜80Hz)は身体に効く。無音の映像作品と、良い音のついた地味な映像作品なら、後者が勝つ。

**5. 完成させて出す。**
未公開の傑作は存在しないのと同じ。3ヶ月かけた70点より、2週間の60点を6回出す方が、作品も評価も速く育つ。

## 9. 個人開発の落とし穴

- **端末差でしか壊れないバグ** — 自分の端末でしか試していない。fpsの可変設計と、低スペック時の劣化パスを最初から入れる
- **自分だけが操作方法を知っている** — 説明なしで他人に触らせるテストを、開発の中盤で必ず1回やる。ここで判明する問題が最も重い
- **観客がいる時に動かない** — 展示当日の照明・電波・人の密度は自室と違う。会場での試験時間を工程に必ず確保する
- **リセットできない** — 誰かが変な状態にした後、自動で初期状態に戻る仕組み。無人時のアトラクトループ
- **著作権・肖像権・個人情報** — 来場者の顔を撮る場合の告知と保存方針。**「顔を撮るか」より「一意識別するか/顔テンプレートを保存するか」が法的な分水嶺であり、これは事後に足せない設計判断である**(`current.md`)。学習済みモデルのライセンス(商用可否)を配布前に確認する

## 10. 野心の3段階と、その使い分け

同じ企画に対して、3つの到達点を分けて考える。混同すると、永遠に完成しないか、志の低いものが出来上がる。

**検証プロトタイプ** — インタラクションが本当に面白いかだけを証明する最小構成。見た目は問わない。1〜2週間。ここで面白くないものは、磨いても面白くならない。

**個人ショーケース** — その制作者が確実に完成させ、人前に出せる完成度の版。**通常の推奨基準はここ。**署名的振る舞い1つに集中し、それを徹底的に磨く。機能追加ではなく、応答性・タイミング・音・見せ方の精度に時間を使う。

**拡張プロダクション** — 予算、協働者、会場、専門的な制作が加わった時に開ける版。**ここから作り始めてはいけない**(既にリソースがある場合を除く)。ただし個人ショーケースの設計時に、拡張への道を塞がないようにする(コアの分離、データ形式の汎用性、スケールしうる写像設計)。

**判断のしかた:** 「理論上の最大値」ではなく「この制作者が今の条件で到達できる最大値」を基準にする。そして**個人ショーケースを、大規模版の縮小コピーとして設計しない。**そのスケールに自然に属する、最も強い体験を探す。

## 11. 個人ビルド戦略の出力構成

スケールS(個人開発)の企画・計画依頼では、選んだモードの構成に次を重ねる。

1. **最も価値の高いコンセプト** — このスケールだからこそ成立するもの
2. **署名的振る舞い** — 記憶に残る一つの振る舞い
3. **最小十分なシステム** — その効果を出せる最も単純な技術構成
4. **推奨する形式** — アプリか、設置か、道具か。理由とともに
5. **1人で現実的に作れる範囲** — 期間と工数の見積
6. **意図的に作らないもの** — 除外を明示することが工数を守る
7. **プロトタイプの順序** — 最も不確実な仮説から
8. **個人ショーケースの目標** — 何をもって「人前に出せる」とするか
9. **拡張の道筋** — 何が加われば次の段階が開くか

**この構成を「暫定版の計画」として書かない。**これがそのプロジェクトの最終形かつ最適形でありうる。

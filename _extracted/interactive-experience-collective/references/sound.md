映像の設計に `protocol.md` の Step 3 があるように、音にも設計がある。**「音も大事です」と書いて終わるのが、この領域で最も多い失敗である。**

## 1. 最初に決める3つ

この3つを決めずに音を作り始めると、必ず作り直しになる。

### ① タイムラインを誰が持つか

| | 音楽が主 | 人が主 |
|---|---|---|
| 構造 | 尺が決まっている。人は乗る | 尺が無い。人が止めれば止まる |
| 向く形式 | ショー、演出、映像作品、常設のループ | 楽器、インスタレーション、パフォーマンス |
| テンポ | 固定。人の動きを拍に量子化する | 人の動きがテンポになる、または拍が無い |
| 失敗の形 | 参加者が「自分は関係ない」と感じる | 何をしても同じに聞こえ、5分で飽きる |

**中間は無い。**どちらかに倒してから、もう一方を限定的に借りる。「拍は固定だが、フィルの位置だけ人が決める」は前者。「自由だが、エコーだけテンポにロックする」は後者。

### ② 音は「説明」か「音楽」か

- **説明（ソニフィケーション）** — 動きを音に写像する。対応が**分かる**。ただし、分かった瞬間に飽きる
- **音楽** — 動きが音楽を生成するが、音楽自体が自立して聴ける。**気持ちいい**。ただし対応が読めなくなり、自分が鳴らした感覚が消える

**実務的な解は2層に分けること。**即時・1対1で対応が読める層（動作に貼り付く音。これが「自分が鳴らした」を作る）と、蓄積して音楽的に自立する層（和声、ドローン、繰り返し）。前者だけだと効果音、後者だけだとBGMになる。

### ③ 遅延の階層をどこに置くか

→ 第3節。**ここは選択ではなく物理的な制約なので、①②より先に効いてくることがある。**

## 2. 中心設計フレーム（音版）

`protocol.md` Step 3 の Trigger → Interpretation → Response → Transformation → Residue を、音では次に読み替える。

**Gesture → Gate → Pitch/Timbre → Space → Memory**

- **Gate（何が発音を起こすか）** — 位置ではなく**運動**で発音させる。位置だけで鳴らすと、静止した手の推定ノイズで機銃射撃になる。速度ゲート、デバウンス、境界のヒステリシスの3点セットで守る
- **Pitch/Timbre（何が音を決めるか）** — 位置が音程、運動が発音、という分離が定石。**音程はスケールに拘束する。**不特定多数が触るものでペンタトニックが選ばれるのは「外れた音が出ない」からで、これは逃げではなく設計判断
- **Space（どこで鳴っているか）** — 定位と残響。ここで「その人の音」と「みんなの音」を分ける
- **Memory（何が残るか）** — 直前に鳴らした音が、その後の音楽に影響を残すか。**ここが空白だと、5分後と5秒後が同じ音になる**

## 3. 遅延予算 — 視覚とは桁が違う

**視覚の 100ms をそのまま音に適用してはいけない。**

| 用途 | 上限 | 根拠 |
|---|---|---|
| **自分の動作が音を出す**（楽器的） | **20〜30ms** | これを超えると「自分が鳴らした」という因果の結びつきが弱まる |
| リズムに合わせる・複数人で拍を揃える | 20ms 前後 | 視覚より要求が厳しい |
| 動作への反応としての音（楽器ではない） | 100ms 前後 | 視覚と同程度でよい |
| 場面転換・環境音の変化 | 数百ms〜 | 気づかれない |

**カメラを使う時点で 20ms は物理的に不可能である。**カメラの露光と転送だけで 30〜60ms、推論を足せばさらに乗る。ここを「頑張って速くする」で解こうとするのが典型的な失敗。

## 4. 遅延は消せない。隠す

**アタックの立ち上がりが遅い音は、遅延を隠す。**

- 撥弦・打楽器系（アタック 5ms 以下）は、遅延をそのまま露出する。60ms 遅れれば 60ms 遅れて聞こえる
- パッド・ベル系（アタック 200〜400ms）は、遅延が立ち上がりの中に埋もれる。**同じ実装遅延でも、体感の即時性がまったく違う**

つまり**音色の選択が遅延対策になる。**カメラ入力で「気持ちよさ」が出ない時、まず疑うのは推論速度ではなく音色のアタックである。

他の手段:
- **予測発音** — 速度から境界の到達を1〜2フレーム先読みして先に鳴らす。行き過ぎると誤発音になるので、速度が十分大きい時だけ適用する
- **視覚を音に合わせて遅らせる** — 音を速くできないなら、映像側を数フレーム遅らせて一致させる。ズレていることの方が、両方遅いことより気持ち悪い
- **持続音に切り替える** — 発音のタイミングを問わない構造（動きが音量やフィルタを連続的に動かす）にすれば、遅延の問題自体が消える

## 5. 音を「鳴らさない」設計

**鳴りっぱなしの体験には強弱が無い。**

- **無音を設計に入れる。**常にパッドが鳴っている構成は、安心感はあるが起伏を殺す。人がいなくなったら止まる、という以上の「休符」を持たせる
- **発音を落とすなら、古い音を止める。**同時発音数の上限に達した時、**新しい音を捨ててはいけない。**ユーザーが動いたのに音が出ないのは、楽器として最悪の失敗である。古い音を減衰させて枠を空ける（ボイススティール）
- **帯域を配る。**複数人・複数音色が同じ音域に集まると互いにマスキングして、全部が濁る。人ごと・役割ごとに音域か音色を分ける。低域（〜120Hz）と空気感（8kHz〜）が空いている構成は、音が「小さくないのに痩せて聞こえる」
- **リミッターを必ず入れる。**同時発音が増えれば合計は簡単に 1.0 を超える。マスターに `DynamicsCompressorNode` か軽いリミッターを1段入れるだけで、割れは消える。これを省いた状態のミックス評価には意味がない

## 6. 音楽的な時間 — 蓄積と展開

5分後に飽きるかどうかは、ここで決まる。

- **和声を動かす。**ルートと調が固定のままだと、どれだけ音色が良くても風景が変わらない。数十秒〜数分の周期でルートを動かすだけで、同じスケール・同じマッピングのまま景色が変わる。ペンタトニックならルート移動でモードの色が変わるので、コストに対する効果が非常に大きい
- **量子化は選択肢にする。**常に拍に吸着させると表現が死ぬ。逆に完全に自由だと複数人で合わない。**エコーやループ層だけ拍にロックし、直接の発音は自由にする**構成が、両立の定石
- **演奏を記録して返す。**直前に鳴らしたフレーズを、音量を落として繰り返す層を持たせると、体験に記憶が生まれる。視覚の「軌跡が残る」に対応する音の Residue がこれ
- **残響は音の彫刻である。**生成ノイズのインパルス応答は「外れない」が「その場所らしさ」が無い。実空間のIR（能舞台、寺の本堂、階段室、廃駅）を1本入れるだけで、音の説得力は明確に変わる。**コンセプトに合う実空間のIRは、最も安上がりな差別化である**

## 7. 個人開発でのスタック

| やりたいこと | 手段 |
|---|---|
| ブラウザで低遅延の合成・処理 | Web Audio API。重い処理は AudioWorklet（メインスレッドで DSP を回さない） |
| 事前制作した音楽の再生と同期 | 音声ファイル + Web Audio のスケジューリング。`setTimeout` で拍を刻まない |
| 作曲・音源制作 | Ableton Live（+ Max for Live）が事実上の標準。SuperCollider は生成音楽に強い |
| 複数プロセス・複数機材の同期 | Ableton Link（テンポ同期）/ MIDI Clock / SMPTE LTC → `software.md` |

**AudioContext は `latencyHint: 'interactive'` で作る。**iOS はユーザー操作の直後でないと解錠されない。この2点は毎回踏む。

## 8. 権利処理 — 遅れて企画を殺す

**商業施設・常設・有料興行で既存曲を使うなら、企画の最初に確認する。**

- **録音物を映像や体験に同期させる** → シンクロ権（原盤権者とのやり取りが要る。取れないことがある）
- **公衆の場で流す** → 演奏権（日本なら JASRAC / NexTone 等の管理団体。施設の包括契約でカバーされる場合とされない場合がある）
- **配信・アーカイブ公開** → さらに別枠

**「有名曲を使う」前提の企画は、権利が取れなかった時に何も残らない。**代替案（オリジナル制作、権利処理済みライブラリ、パブリックドメイン）を最初から並べておく。オリジナル制作は、費用よりも**納期**でスケジュールを壊しやすい。

生成AIによる楽曲・音声は、商用利用条件と学習データの出所が案件ごとに問題になる。施主が公共・企業なら、確認を先に置く。

## 9. 聴覚アクセシビリティ

- **音だけで伝わる情報を作らない。**聴覚障害のある来場者に、体験の中心が届かなくなる
- **音の代替を用意する。**振動（トランスデューサ、スマートフォンのハプティクス）、光の同期、字幕
- **音過敏への配慮。**光過敏の警告（`process.md`）と同様に、突発的な大音量・高周波の持続音は掲示するか避ける。自閉スペクトラムの来場者にとって、音は光と同じかそれ以上の負荷になる
- **音量の上限を決めて掲示する。**「大きい方が没入する」は誤り。長時間の運用では聴覚保護の問題にもなる

## 10. 出力構成（音が体験の中心を占める案件で、選んだモードに重ねる）

1. **タイムラインの所有者**（音楽が主か、人が主か。理由）
2. **説明の層と音楽の層**（何が1対1で対応し、何が自立するか）
3. **Gesture → Gate → Pitch/Timbre → Space → Memory**
4. **遅延予算と、それをどう満たすか**（隠すのか、速くするのか、構造で回避するのか）
5. **時間展開**（何分もつか。何が変化して飽きを防ぐか）
6. **権利処理の状態**（オリジナルか既存曲か。既存曲なら誰と交渉するか）

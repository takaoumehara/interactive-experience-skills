スタック提案は必ず: **選定 / 理由 / 代替とトレードオフ / アーキテクチャ図(テキストで可) / パフォーマンス予算 / 劣化ラダー** をセットで出す。

**技術名を並べない。**このファイルの使い方は「出したい表現 → それを出せる最も安い手段 → 代償」であって、選択肢の列挙ではない。表現から入れない場合は `feel.md` を先に読む。

## 1. 最初の分岐 — 分散構成か、単体完結か

```
複数機材・多面出力・会場設置・ショー制御あり ──→ 分散構成（第2節）
1人〜少人数、ブラウザまたは端末で完結 ────────→ 単体完結（第3節）
```

**分散構成が定石なのは設置スケールだけ。**例「Unreal(絵作り) + TouchDesigner(センサー統合・ショー制御) + Python(AI推論)」のように各層を疎結合にして通信で繋ぐ方が本番で強い。

**個人開発・低予算スケールでは逆。**分散構成は運用コストが高く、1人では維持できない。Web単体またはネイティブ単体に振り切る方が、配布性・堅牢性・完成確率すべてで勝る。

## 2. 分散構成（設置スケール）

```
リアルタイム3D・フォトリアル・大画面 ─────→ Unreal Engine（nDisplayでマルチ画面同期）
ノードベースで映像・センサー・音を統合 ───→ TouchDesigner（業界のハブ。迷ったらまずこれ）
ゲームロジック・モバイル/AR併用・チーム ──→ Unity
2D/パーティクル中心・アーティスト主導 ────→ TouchDesigner or Notch
研究的・カスタムアルゴリズム・C++制御 ────→ openFrameworks / Cinder
AI生成（画像/潜在空間/追跡）───────────→ Python(PyTorch) を別プロセス化し OSC/NDI で接続
```

### パターンA: センサー駆動インスタレーション(最頻出)
```
[LiDAR/深度カメラ] → [トラッキングプロセス(Python/専用SW)]
        │ OSC (人物ID, x, y, 速度)
        ▼
[TouchDesigner/Unreal: ワールド状態+レンダリング] → [プロジェクター/LED]
        │ OSC/DMX(Art-Net)
        ▼
[照明] [音響エンジン(Ableton+Max / ゲームエンジン内蔵)]
```
- トラッキングと描画を別プロセス/別マシンに分離 — 描画が落ちてもトラッキングは生きる
- 人物IDの永続化(ロスト時の再割当)が体験品質を決める。ロスト許容 0.5-1秒でスムージング

### パターンB: マルチディスプレイ同期(大型LED/多面プロジェクション)
- Unreal nDisplay または メディアサーバー(disguise / Watchout クラス)
- 同期はゲンロック/NDI/独自フレームロック。「ズレていないか」をコンテンツに検証パターンとして仕込む

### パターンC: AI生成連動
```
[入力(カメラ/音声/テキスト)] → [Python推論サーバー(GPU)] → [NDI/Spout/Syphonで映像返却] → [TD/Unrealで合成]
```
- 生成レイテンシは隠す演出で吸収(トランジション、粒子化)。「待たせている」と感じさせたら負け
- Diffusion系のリアルタイム化は蒸留モデル+低ステップが現実ライン(要最新状況の確認)

## 3. 単体完結 — Web

ブラウザは本格的なリアルタイム表現環境である。**インストール不要・審査不要・URLひとつで届く**という配布上の優位は、技術的制約を補って余りある。設置作品は会場に行かないと体験できないが、Web作品は開いた瞬間に始まる。

### 3-1. 描画手段の選定

| 出したい表現 | 手段 | 代償 | 壊れ方 |
|---|---|---|---|
| 数万〜数十万粒子の並列計算、リアルタイム流体、高精度ポストエフェクト | **WebGPU / WGSL**(Compute Shader) | フォールバックの二重実装が必須 | 非対応環境で何も出ない |
| 拡散・滲み・GPUセルオートマトン、ライブラリ非依存の軽量構成 | **WebGL2 + 生GLSL** | 自前で書く量が多い | — |
| 3Dシーン、オブジェクト、ノードベースのシェーダー記述 | **Three.js**(TSL / WebGPURenderer) / **React Three Fiber** | バンドルが重い(数百KB〜) | — |
| 最高速の2Dスプライトとシェーダー | **PixiJS** | 3Dは守備範囲外 | — |
| 3Dだが数十KB以内に収めたい | **OGL** | 機能が薄く、自分で書く | — |
| ベクターのインタラクティブアニメーションを数KBで | **Rive** | 表現の天井が低い。**配布重量が絶対条件の時だけ** | — |
| 3D/シェーダーをノーコードで作って埋め込む | **Spline** | ランタイムが重い。細かい制御が効かない | — |
| 写真・動画から実写空間を再構築して歩く | **3D Gaussian Splatting** | シーンが数十MB。**静的シーンであり、動かせるのはカメラだけ** | 配布性という最大の武器を自分で壊す |

### 3-2. アルゴリズム描画 — 既視感から抜けるための語彙

軌跡・パーティクル・骨格線は2010年頃から無数にある(`movement.md` §5)。そこから抜けるには、**別の生成原理**が要る。

| 原理 | 出せるもの | 向く触感(`feel.md`) |
|---|---|---|
| **メタボール**(距離場) | 有機的に結合・分離・伸縮する。スライム、細胞、液体 | 1 粘性 / **2人の関係を描くのに最適** |
| **L-System** | ツタ・枝葉が数学的に成長し、花が開く | 8 成長 |
| **拡散反応 / セルオートマトン** | 滲み、斑紋、痕跡が残り干渉する | 8 成長 / 11 内面 |
| **流体(Navier-Stokes)** | 渦、乱流、押し分け | 1 粘性 / 4 重さ |
| **物理シミュレーション**(バネ・慣性) | 素直に従わない。抵抗する | 2 弾性 |

**メタボールは特に見落とされている。**2人の距離場が融合・分離するさまは、骨格線や軌跡より遥かに「関係」が見える。複数人を主変数にする企画では第一候補になる。

### 3-3. 劣化ラダー — WebGPU を選ぶなら宣言必須

「fps の可変設計を入れる」では足りない。**設計時に階段を宣言する。**

```
WebGPU Compute（流体・数十万粒子）
   ↓ 非対応 / 性能不足
WebGL2（セルオートマトン・数万粒子・transform feedback）
   ↓ さらに不足
2D（PixiJS）または粒子数を1/10
   ↓ さらに不足
Rive / 事前生成のアニメーション or 静止画
```

実測fpsで粒子数を可変にする。自分の端末でしか試していないのが、この領域で最も多い失敗。

### 3-4. 配布重量の予算 — 配布性を主張するなら、バイトを予算化する

個人スケールの構造的な優位は配布性である。**重さを予算化しない限り、その優位は守れない。**

| 帯 | 何が入るか | 体感 |
|---|---|---|
| 〜100KB | Rive / OGL / 生WebGL2 | 一瞬で始まる。SNS流入に耐える |
| 〜1MB | Three.js + 自前シェーダー + Web Audio | 実用上ほぼ問題ない |
| 〜5MB | 上記 + オンデバイス推論モデル + 音素材 | 初回だけ待たせる。ローディングを体験にする |
| 10MB〜 | Spline のシーン、3DGS のシーン、動画素材 | **URLで配る利点が消え始める。**ここを超えるなら、その理由を言えること |

### 3-5. 取れる入力 / 出せる出力

**入力** — カメラ(`getUserMedia`) → 姿勢/手/顔/セグメンテーション(オンデバイス推論) / マイク → 音量・周波数・ピッチ・音声認識 / 端末センサー(`DeviceMotionEvent`、方位、位置) / タッチの圧力・面積・複数指 / 他端末との通信(WebRTC / WebSocket)

**出力** — WebGPU・WebGL2 / Web Audio(合成・空間化・実時間処理) / WebCodecs(動画の実時間処理と書き出し) / `navigator.vibrate`

**ブラウザだからこその表現** — URLに状態を埋めて作品を送り合う / 複数端末を並べて1つの絵を作る / QRで即参加、会場設営ゼロ / 同じ作品がPC・スマホ・投影で別の体験になる

**限界を先に知る:** iOSのモーションセンサーはユーザー許可が必要。バックグラウンドで動かない。**音声再生はユーザー操作が起点でないと解錠されない。**GPUは端末差が大きい。

## 4. 単体完結 — Apple ネイティブ

「一度体験して終わる」ものは Web、**「毎日身体を動かす」ものはネイティブ**。この分岐が最初に効く。

| 手段 | 何のためか |
|---|---|
| **Metal / MSL** | GPUを直接駆動する最速・最安のローレベルAPI。重い生成処理はここ |
| **SwiftUI Shader Modifiers**(`.colorEffect` / `.distortionEffect` 等) | 既存のSwiftUI画面に**1行で**シェーダーを適用する。**個人開発で費用対効果が最も高い項目のひとつ** |
| **RealityKit / Reality Composer Pro** | 3D/AR/空間レンダリング。visionOS/iOS/macOS |
| **AVAudioEngine / Core Audio** | 超低遅延のノードベース音声処理 → `sound.md` |
| **Audio Unit (AUv3)** | システムレベルのシンセ・プラグイン。他アプリから使われる資産になる |

**判断:** 独自の質感が欲しいだけなら、Metal を書く前に SwiftUI Shader Modifiers で足りることが多い。**visionOS は技術的には強いが、作品の出口としては観客の母数が小さい。**そこに人がいるかを確認せずに器として選ばない。

## 5. 通信プロトコル早見

| 用途 | プロトコル |
|---|---|
| センサー→エンジン、エンジン間イベント | OSC (UDP。順序保証が要るならTCP併用) |
| 映像のプロセス間共有(同一マシン) | Spout (Win) / Syphon (Mac) |
| 映像のネットワーク伝送 | NDI |
| 照明 | DMX512 / Art-Net / sACN |
| 音楽同期 | Ableton Link / MIDI Clock / SMPTE LTC |
| 端末間の低遅延データ | WebRTC DataChannel |
| 産業機構(モーター群) | CAN / EtherCAT / Modbus |

## 6. パターンD: 映像を送らず、特徴量だけを送る

**設営ゼロで大画面体験を成立させる構成。**プライバシー上も強い。

```
スマートフォン（カメラ + オンデバイス推論 + 特徴量抽出）
   │ WebRTC DataChannel / ローカル通信
   ▼
TV・PCブラウザ（大画面で描画 + 音響）
```

- **映像そのものは送らない。**送るのは座標か、そこから導いた30〜80個の派生値だけ。全ランドマークを送るより軽く、安定し、プライバシーにも有利
- QRを読むだけで設営が終わる。設置型センサーが要らない
- **発展形:** 参加者それぞれのスマホを分散センサー網にする。各自の端末で処理し、座標だけを会場スクリーンへ送る。映像が端末を出ない構造のまま、多人数参加が成立する
- 高齢者向けではアプリDLと自撮り姿勢が障壁になる。「TVに映る・家族が誘う」形が実解

**注意:** ランドマークデータも身体情報である。「映像じゃないから安全」と扱わない。オンデバイス処理・保存しない・特徴量の最小化を最初から設計に入れる。

## 7. パフォーマンス予算(設計時に宣言する)

- **フレームレート:** 展示は60fps死守(30fpsは「重い」と体感される)
- **入力→反応レイテンシ:** 身体インタラクションは合計100ms以下。**楽器的な体験は50ms以下**(センサー20ms+処理30ms+描画+表示遅延)
- **音声スレッドの隔離:** DSPをメインスレッドで回さない(Web なら AudioWorklet)。**描画負荷が跳ねた時は描画を落として音を守る。**動いたのに音が出ないのは、楽器として最悪の失敗
- **GPU予算:** 4K@60fpsのリッチな生成系は最上位クラスGPU1枚/出力面が目安。常設は3年でのGPU更新費を計上
- **起動と復帰:** 電源ONから無人で本番状態になるまで自動化。展示の朝は誰も端末を触らない前提で作る

## 8. ショー制御・運用レイヤー

- ステート管理: アイドル → アトラクト(客寄せ) → 体験中 → リザルト → アイドル。**無人時のアトラクトループを必ず作る**(棒立ちの画面は死んだ展示)
- 遠隔監視: ヘルスチェック(fps, センサー生存, 温度)をダッシュボード化し、異常時は通知+自動再起動
- コンテンツ更新: 常設は非エンジニアが差し替え可能なCMS/設定ファイル化
- ログ: 体験人数、滞在時間、インタラクション回数を匿名で記録

## 9. 擬似コード提供の指針

実装案を求められたら、動作の核心だけを短い擬似コード/ノード構成で示す。全文コードより「この20行が体験の心臓」を示す方が価値が高い。

例(群衆の位置→パーティクル流の干渉):
```glsl
// compute shader: 各パーティクルは流れ場に従い、人物位置から斥力/引力を受ける
vec2 flow = curlNoise(p.xy * scale + time * drift);
for (int i = 0; i < personCount; i++) {
    vec2 d = p.xy - persons[i].xy;
    flow += normalize(d) * influence / (dot(d,d) + eps);  // 斥力。符号反転で引力
}
p.xy += flow * dt;
```

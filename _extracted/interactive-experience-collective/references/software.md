スタック提案は必ず: **選定 / 理由 / 代替とトレードオフ / アーキテクチャ図(テキストで可) / パフォーマンス予算** をセットで出す。

**バージョン・価格・ライセンス条件は `current.md` にある。**各ツールの現行版、料金体系、メジャーな方針転換(サポート終了、次期メジャーへの移行時期)を確認せずに選定を断定しない。**常設案件では「そのバージョンが何年運用できるか」が選定理由の一部になる。**

## 1. スタック選定フローチャート

```
リアルタイム3D・フォトリアル・大画面 ─────────→ Unreal Engine (nDisplayでマルチ画面同期)
ノードベースで映像・センサー・音を高速に統合 ──→ TouchDesigner (業界のハブ。迷ったらまずこれ)
ゲームロジック・モバイル/AR併用・チーム開発 ──→ Unity
ブラウザ配布・スマホ参加型・設置レス ────────→ WebGL/WebGPU (Three.js / PlayCanvas)
2D/パーティクル中心・アーティスト主導 ───────→ TouchDesigner or Notch
研究的・カスタムアルゴリズム・C++制御 ───────→ openFrameworks / Cinder
AI生成(画像/潜在空間/追跡) ─────────────→ Python (PyTorch) を別プロセス化しOSC/NDIで接続
```

**ハイブリッドが定石:** 例「Unreal(絵作り) + TouchDesigner(センサー統合・ショー制御) + Python(AI推論)」。1ツールで全部やろうとするより、各層を疎結合にして通信で繋ぐ方が本番で強い。

**ただし個人開発・低予算スケールでは逆。**分散構成は運用コストが高く、1人では維持できない。Web単体(ブラウザで完結)またはiOS単体(端末で完結)に振り切る方が、配布性・堅牢性・完成確率すべてで勝る。その場合の具体的な構成と到達点は `solo-scale.md` を参照。身体・動きを入力にする場合は `movement.md` の取得手法比較と遅延設計を必ず併読する。

## 2. 定番アーキテクチャパターン

### パターンA: センサー駆動インスタレーション(最頻出)
```
[LiDAR/深度カメラ] → [トラッキングプロセス(Python/専用SW)]
        │ OSC (人物ID, x, y, 速度)
        ▼
[TouchDesigner/Unreal: ワールド状態+レンダリング] → [プロジェクター/LED]
        │ OSC/DMX(Art-Net)
        ▼
[照明] [音響エンジン(Ableton+Max / ゲームエンジン内蔵)]
```
- トラッキングと描画を別プロセス/別マシンに分離 — 描画が落ちてもトラッキングは生きる
- 人物IDの永続化(トラッキングロスト時の再割当ロジック)が体験品質を決める。ロスト許容時間0.5-1秒でスムージング

### パターンE: 実空間の再現(3D Gaussian Splatting)
- 実在する場所・物・人を空間として再現したい場合、フォトグラメトリ/メッシュより先に **3D Gaussian Splatting** を検討する。撮影→再構成→編集→リアルタイム再生まで商用ツールが揃った
- **ただしエンジンによってネイティブ対応の有無が分かれる。**「どのエンジンを選ぶか」が「スプラットをどれだけ楽に扱えるか」と直結する。対応状況は `current.md`

### パターンB: マルチディスプレイ同期(大型LED/多面プロジェクション)
- Unreal nDisplay または メディアサーバー(disguise / Watchout クラス)
- 同期はゲンロック/NDI/独自フレームロック。「ズレていないか」をコンテンツに検証パターンとして仕込む

### パターンC: 観客のスマホ参加型
- WebSocket サーバー(Node.js) + ブラウザクライアント(QRで参加) + 会場側レンダラー
- 会場Wi-Fiは信用しない: 同時接続数の1.5倍でキャパ設計、参加はキュー制御
- レイテンシ要件が緩い演出(投票、色送信)に限定。リアルタイム操作(ゲーム的)は専用回線でも100ms超を前提に設計

### パターンD: AI生成連動
```
[入力(カメラ/音声/テキスト)] → [Python推論サーバー(GPU)] → [NDI/Spout/Syphonで映像返却] → [TD/Unrealで合成]
```
- 生成レイテンシは隠す演出で吸収(トランジション、パーティクル化)。「待たせている」と感じさせたら負け
- **リアルタイム生成の判断軸が「できるか」から「どこで回すか」に変わった。**ライブ入力を受けて時間的一貫性を保った生成が実用段階に入った一方、実用構成はデータセンター級GPUかクラウド従量課金が前提である。**長期常設ならローカル、短期イベントならAPI従量**という分岐を、演出内容を決める前に済ませる。ローカル完結なら解像度・fps・モデルサイズのどれかを必ず妥協する。現況の数値は `current.md`
- **映像の理解(何が起きているかをAIに読ませる)はリアルタイムに届いていない。**軽量CVでイベントを取り、数秒に1回だけモデルを叩くハイブリッドにする

## 3. 通信プロトコル早見

| 用途 | プロトコル |
|---|---|
| センサー→エンジン、エンジン間イベント | OSC (UDP。順序保証が要るならTCP併用) |
| 映像のプロセス間共有(同一マシン) | Spout (Win) / Syphon (Mac) |
| 映像のネットワーク伝送 | NDI |
| 照明 | DMX512 / Art-Net / sACN |
| 音楽同期 | Ableton Link / MIDI Clock / SMPTE LTC |
| 産業機構(モーター群) | CAN / EtherCAT / Modbus |

## 4. パフォーマンス予算(設計時に宣言する)

- **フレームレート:** 展示は60fps死守(30fpsは「重い」と体感される)。ProMotion的な120fpsは費用対効果低
- **入力→反応レイテンシ:** 身体インタラクションは合計100ms以下を目標(センサー20ms+処理30ms+描画+表示遅延)。楽器的体験は50ms以下
- **GPU予算:** 4K@60fpsのリッチな生成系は最上位クラスGPU1枚/出力面が目安。**「毎年更新して性能を買う」前提は現在成立しない。**今ある世代で3年戦う設計と、予備機の同時確保を見積に入れる(現況は `current.md`)
- **起動と復帰:** 電源ONから無人で本番状態になるまで自動化(自動ログイン→ウォッチドッグ→アプリ起動→自己診断)。展示の朝は誰も端末を触らない前提で作る

## 5. ショー制御・運用レイヤー

- ステート管理: アイドル → アトラクト(客寄せ) → 体験中 → リザルト → アイドル。無人時のアトラクトループを必ず作る(棒立ちの画面は死んだ展示)
- 遠隔監視: ヘルスチェック(fps, センサー生存, 温度)をダッシュボード化し、異常時は通知+自動再起動
- コンテンツ更新: 常設は非エンジニアが差し替え可能なCMS/設定ファイル化。「更新できない展示」は1年で陳腐化する
- ログ: 体験人数、滞在時間、インタラクション回数を匿名で記録 — 次の提案の武器になる(施主報告にも使える)

## 6. 擬似コード提供の指針

実装案を求められたら、動作の核心だけを短い擬似コード/ノード構成で示す。全文コードより「この20行が体験の心臓」を示す方が価値が高い。

例(群衆の位置→パーティクル流の干渉):
```glsl
// compute shader: 各パーティクルは流れ場に従い、人物位置から斥力/引力を受ける
vec2 flow = curlNoise(p.xy * scale + time * drift);
for (int i = 0; i < personCount; i++) {
    vec2 d = p.xy - persons[i].xy;
    flow += normalize(d) * influence / (dot(d,d) + eps);  // 斥力。符号反転で引力
}
p.xy += flow * dt;
```

# 引き継ぎパケット — テンプレート

director が専門スキルへ渡す時、および専門スキル間で引き渡す時に、この形で出力する。**会話全体を要約しない。**専門スキルが設計を始めるのに必要な情報だけを渡す。

## 書き方の規則

- **不明な項目は空欄にせず「未確定」と書き、確定させる方法を1行添える。**空欄は「情報がない」のか「聞き忘れた」のか区別できず、専門スキル側で必ず事故になる
- **仮定で埋めた項目は `(仮定)` を付ける。**仮定を事実として渡すことが、この受け渡しで最も高くつく失敗
- 全体で15〜25行に収める。これを超えるなら、専門スキル側で決めるべきことを director が抱え込んでいる

---

## テンプレート

```markdown
## 引き継ぎ: <案件名> → <専門スキル名>

**目的** — 何のためのシステムか。一文
**使う人** — 誰が実際に操作・体験するか。属性ではなく具体的な人物像
**払う人** — 誰が金を出すか。使う人と同じなら「同一」と明記する
**中核の痛み** — 今どこで困っているか。機能ではなく困りごとで書く
**良くなるべきこと** — 何がどう改善されれば成功か。観測可能な形で
**使用文脈** — いつ、どこで、何分間、どんな状態で使われるか
**現段階** — 技術のみ / 課題仮説 / ユーザー確定 / 痛み検証済 / 試作あり / 有償顧客あり
**制約** — 予算 / チーム規模 / 端末・機材 / 期限 / プライバシー・同意条件
**未検証の前提** — この案件が崩れるとしたらどれか。危険な順に最大3つ

**このスキルに決めてほしいこと** — 具体的な問いの形で。1〜3個
**必要な成果物** — 何が出てくれば次に進めるか

**director が既に下した判断（覆すなら理由を示すこと）**
- 例: 形式はアプリとする。設置は検討済みで除外
- 例: 2台目のカメラは現段階では足さない

**今回は扱わないこと** — 意図的な除外。理由付きで
```

## 記入例

```markdown
## 引き継ぎ: 道場向け稽古記録 → movement-learning-system-designer

**目的** — 週2回の稽古の間に生徒が指摘を忘れる問題を、指導者の負担を増やさずに埋める
**使う人** — 指導者(50代、スマホは使うがPCは使わない)。生徒は閲覧のみ
**払う人** — 道場(月謝からの付加サービス)。生徒個人ではない
**中核の痛み** — 指導者が20人を同時に見られず、同じ指摘を毎週繰り返している
**良くなるべきこと** — 同一の指摘の反復回数が減る。指導者の稽古後作業が5分以内
**使用文脈** — 稽古直後の道場、5分以内、立ったままスマホ片手
**現段階** — 課題仮説。ユーザー未確定、痛みは指導者1名の証言のみ
**制約** — 個人開発1名、予算〜5万、iPhone想定、未成年の撮影あり(保護者同意が前提条件)
**未検証の前提** —
1. 指導者が稽古後に5分を割く意思がある
2. 生徒が動画を実際に見返す
3. 指摘の反復が実際に上達を妨げている(逆に反復こそが指導という可能性)

**このスキルに決めてほしいこと**
1. 自動評価を入れるべきか、指導者の手入力で足りるか
2. カメラは1台で足りるか、どの角度か
3. 最初に対象とする技を1つに絞るならどれか、その基準

**必要な成果物** — MVPの範囲定義と、2週間で判定できる検証計画

**director が既に下した判断（覆すなら理由を示すこと）**
- 生徒向けアプリではなく指導者向けの道具とする。払う人が道場のため
- 採点・スコア表示は入れない。動機を削るリスクが利益を上回る

**今回は扱わないこと** — 複数道場への展開、カリキュラム機能、課金。1道場で価値が出る前に作らない
```

## 受け取った側の最初の仕事

1. **「このスキルに決めてほしいこと」に答えられるか確認する。**答えられないなら、何が足りないかを director に返す
2. **`(仮定)` の付いた項目のうち、設計の根幹に関わるものを特定する。**根幹が仮定の上に乗っているなら、設計より先にそれを潰す計画を出す
3. **「director が既に下した判断」に異論があれば、明確な理由と移行コストとともに言う。**黙って別の前提で設計しない
